* Structure-aware editing tools
** TODO Structure-aware editors cannot target a free-standing comment block
   =lisp-edit-form= and =lisp-patch-form= operate on *named top-level forms*. A
   =;;;= banner / section comment that sits *between* top-level forms — not
   reachable as text inside any =(defun …)= / =(defmethod …)= body — has no
   handle. There is no verb to replace or patch such a comment block.

   Reproduction: =seven/src/transport-socket.lisp= has a multi-line =;;;=
   section comment ("SCM_RIGHTS fd passing — sideband over an AF_LOCAL
   endpoint") between the =close= method and the first alien-routine
   definition. A doc-accuracy pass needed to rewrite it. =lisp-patch-form=
   scopes *within* a matched form and =lisp-edit-form= matches a *whole* form,
   so neither can address a comment that is not inside a form.

   Impact: the only fix was a plain text edit — which the DSMR workflow forbids
   for =.lisp= files, defeating the point of the structure-aware tools. Every
   comment-accuracy pass over banner/section comments hits this.

   Suggested fix:
   - Let =lisp-patch-form= / =lisp-edit-form= scope to the *leading comment*
     attached to a named form (edit the comment without touching the form), and
   - add a comment-region verb (anchor by first/last line or a unique
     substring) for banner comments that belong to no single form.

** DONE lisp-edit-form cannot match a form whose name is a compound spec (e.g. define-alien-routine)
   Fixed: =%definition-candidates= (=src/lisp-edit-form-core.lisp=) now walks a
   compound name spec and emits a candidate for every symbol it contains, so the
   Lisp-side name in a =(c-name lisp-name)= spec is matchable. General rule, not a
   =define-alien-routine= special case, so =define-alien-variable= and kin work too.
   Regression tests in =tests/lisp-edit-form-test.lisp= (tool-level repro +
   =%definition-candidates= unit case). Description below kept for the record.

   The name-extraction logic assumes =(defX name …)= with =name= a bare symbol
   at position 1, so a form whose name lives inside a spec list is unreachable.
   =sb-alien:define-alien-routine= names the Lisp function as the *second
   element of a =(c-name lisp-name)= list*:

   #+begin_src lisp
   (sb-alien:define-alien-routine ("sendmsg" %scm-sendmsg) sb-alien:long
     (fd sb-alien:int) (msg sb-alien:system-area-pointer) (flags sb-alien:int))
   #+end_src

   Reproduction (against =seven/src/transport-socket.lisp=):

   #+begin_example
   lisp-edit-form
     form_type = "define-alien-routine"
     form_name = "%scm-sendmsg"
     operation = replace  (dry_run true)
   => "Form define-alien-routine %scm-sendmsg not found in …/transport-socket.lisp"
   #+end_example

   The form is present and loads fine; it is simply not matchable.

   Impact: such forms — and their leading comments/docstrings — cannot be
   edited structurally, forcing a fall-back to the generic text editor. Compounds
   with the comment-block issue above when a banner comment precedes a
   =define-alien-routine=.

   Suggested fix: extend the matcher so that when the element after =form_type=
   is a *list*, the name is resolved from the spec rather than skipping the
   form. For =define-alien-routine= the Lisp name is =(second name-spec)=. The
   same =(external internal)= shape appears in =define-alien-variable= and other
   =sb-alien= def-forms, so prefer a general "if the name position is a list,
   search it for the symbol matching =form_name=" rule over special-casing one
   macro.

   Note: both limitations were hit during ordinary doc/comment maintenance on a
   loaded, compiling system — not exotic input. Until fixed, the workaround is a
   plain-text edit followed by =lisp-check-parens= + =load-system= to prove
   structure was not disturbed.
* Parallel agent execution vs. ASDF system resolution
** TODO Worktree isolation does not isolate ASDF: a hotloading agent can resolve a worktree it does not own
   Running several editing agents concurrently against one repo is unsafe — they
   share one git working tree and one attached image, so branches collide and
   every cold verify is contaminated by another agent's in-flight edits. The
   standard remedy is to give each agent its own git worktree. For Common Lisp
   that remedy is incomplete, and the gap is quiet rather than loud.

   A worktree isolates the *filesystem*. ASDF's system namespace is *global* and
   keyed by system **name**, not by path. N worktrees of this repo are N
   directories each containing a =dsmr-mcp.asd= that all claim the name
   =dsmr-mcp=. Which one a given image loads is decided by source-registry
   search order, not by which worktree the agent was assigned. An agent can
   therefore compile, load, and test code it does not own, and report green — the
   same "a green certifies nothing" failure that worktrees were introduced to
   prevent, now harder to spot because the filesystem looks correctly isolated.

   Reproduction (the hazard is already in-tree, in two spots):

   #+begin_src lisp
   ;; src/hermetic/worker-client.lisp — inherited config is consulted FIRST,
   ;; and the explicit source is a :tree scan rather than a pinned directory.
   (asdf:initialize-source-registry
     '(:source-registry :inherit-configuration (:tree #p"...")))

   ;; src/bus/broker.lisp — the correct shape: explicit directory wins,
   ;; inherited config only fills in the remainder.
   (asdf:initialize-source-registry
     '(:source-registry (:directory #p"...") :inherit-configuration))
   #+end_src

   =src/lsp/client.lisp= repeats the worker-client form. With sibling worktrees
   under a scanned root, the =:tree= variant sweeps up every one of them, and the
   leading =:inherit-configuration= means anything resolvable from the global
   configuration outranks the source directory the worker was explicitly handed.

   Impact: blocks safe parallel agent execution, which is the actual goal. Today
   the only defensible posture is to serialize editing agents on a shared repo,
   which costs real throughput on every multi-plan piece of work. It also means
   the existing hermetic worker is less hermetic than its name claims — a
   pre-existing correctness question independent of parallelism. A related
   failure has already been observed with tree scans picking the wrong version of
   a dependency that ships many copies.

   Suggested fix:
   - Normalize every registry initialization to the broker's shape: the owned
     directory as an explicit =(:directory ...)= entry FIRST, =:inherit-configuration=
     last, and never =(:tree ...)= over a root that can contain sibling checkouts.
   - Give each parallel agent a source registry naming exactly the worktree it
     owns, so system-name resolution cannot reach a sibling regardless of what
     else is registered.
   - Keep worktrees out of any directory covered by an inherited tree scan
     (notably a local-projects tree), or they self-register and re-open the hole.
   - Give each agent its own fasl cache (=XDG_CACHE_HOME=); shared caches have
     already produced a flavor-mismatch crash here.
   - Then verify the property directly rather than assuming it: two agents, two
     worktrees, a deliberate divergence between them, and an assertion that each
     loads its own definition. Until that test exists, parallel Lisp execution
     should stay off.

* IPC Bus faults in practice (Burn Down)
** TODO the bus polling is too noisy, and an agents own bus emissions trip their own watches
   Update: the "own emissions" half is fixed. The wakeup watcher already filters a
   record carrying the agent's own encoded self-id, and =bus-status='s pending
   count now applies that same filter — it previously counted an agent's own
   un-consumed publishes, so status reported mail =bus-receive= would never hand
   back, read as loss. Count and delivery now share one foreign-record predicate
   (=envelope:foreign-record-p=) so they cannot drift apart again. Tracked in #48
   (fixed). The remaining half — poll cadence being too noisy — is unaddressed.
