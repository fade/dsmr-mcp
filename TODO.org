* Structure-aware editing tools
** DONE Structure-aware editors cannot target a free-standing comment block
   CLOSED: 2026-07-30

   Fixed: the =lisp-edit-comment= verb replaces or deletes a comment that
   belongs to no form. Region mode names a free-standing banner by a unique
   substring of it, narrowed by a line range when the substring alone is
   ambiguous. Leading mode names the form the comment sits flush on top of,
   which is what reaches a file header written against =(in-package …)=, the
   shape the second reproduction below is about. Replace and delete are the
   whole operation set; placing a brand new comment relative to a form is
   already what =lisp-edit-form= =insert_before= does.

   Two things make the verb safe to point at real files. Every surrounding form
   is compared byte for byte at its shifted offset before anything is written,
   so a replacement that would swallow neighbouring code into comment text is
   refused rather than applied, and a delimiter scan alone does not see that
   case. And an anchor naming no comment, or more than one, reports the
   candidates instead of guessing, naming the form that claims the text so a
   caller who reached for the wrong mode is told which one would have worked.

   Implementation in =src/lisp-edit-comment-core.lisp=,
   =src/lisp-edit-comment.lisp= and =src/tools/lisp-edit-comment.lisp=, tests in
   =tests/lisp-edit-comment-test.lisp=. Description below kept for the record.

   =lisp-edit-form= and =lisp-patch-form= operate on *named top-level forms*. A
   =;;;= banner / section comment that sits *between* top-level forms — not
   reachable as text inside any =(defun …)= / =(defmethod …)= body — has no
   handle. There is no verb to replace or patch such a comment block.

   Reproduction: =seven/src/transport-socket.lisp= has a multi-line =;;;=
   section comment ("SCM_RIGHTS fd passing — sideband over an AF_LOCAL
   endpoint") between the =close= method and the first alien-routine
   definition. A doc-accuracy pass needed to rewrite it. =lisp-patch-form=
   scopes *within* a matched form and =lisp-edit-form= matches a *whole* form,
   so neither can address a comment that is not inside a form.

   Impact: the only fix was a plain text edit — which the DSMR workflow forbids
   for =.lisp= files, defeating the point of the structure-aware tools. Every
   comment-accuracy pass over banner/section comments hits this.

   Second reproduction: a *file header* (SPDX block plus leading commentary)
   above every top-level form, not between two of them. This spelling makes the
   gap total rather than awkward, because =fs-write-file= refuses to overwrite an
   existing =.lisp= file by design, correctly, so out-of-form text has no
   compliant route at all.

   Which mode reaches a header turns on a blank line, and the intuitive choice is
   wrong in the common case: separated from the first form the header is a
   free-standing region matched by substring, but flush against the first form it
   is that form's leading comment and free-standing matching misses it. Flush
   against =(in-package …)= is the ordinary shape. It is reachable, since
   =%definition-candidates= accepts a keyword in the name position, so
   =in-package= is matchable by form type plus name, but no absent-anchor error
   would tell a caller to look there. Fix that error text alongside the verb.

   Suggested fix:
   - Let =lisp-patch-form= / =lisp-edit-form= scope to the *leading comment*
     attached to a named form (edit the comment without touching the form), and
   - add a comment-region verb (anchor by first/last line or a unique
     substring) for banner comments that belong to no single form.

** DONE lisp-edit-form cannot match a form whose name is a compound spec (e.g. define-alien-routine)
   Fixed: =%definition-candidates= (=src/lisp-edit-form-core.lisp=) now walks a
   compound name spec and emits a candidate for every symbol it contains, so the
   Lisp-side name in a =(c-name lisp-name)= spec is matchable. General rule, not a
   =define-alien-routine= special case, so =define-alien-variable= and kin work too.
   Regression tests in =tests/lisp-edit-form-test.lisp= (tool-level repro +
   =%definition-candidates= unit case). Description below kept for the record.

   The name-extraction logic assumes =(defX name …)= with =name= a bare symbol
   at position 1, so a form whose name lives inside a spec list is unreachable.
   =sb-alien:define-alien-routine= names the Lisp function as the *second
   element of a =(c-name lisp-name)= list*:

   #+begin_src lisp
   (sb-alien:define-alien-routine ("sendmsg" %scm-sendmsg) sb-alien:long
     (fd sb-alien:int) (msg sb-alien:system-area-pointer) (flags sb-alien:int))
   #+end_src

   Reproduction (against =seven/src/transport-socket.lisp=):

   #+begin_example
   lisp-edit-form
     form_type = "define-alien-routine"
     form_name = "%scm-sendmsg"
     operation = replace  (dry_run true)
   => "Form define-alien-routine %scm-sendmsg not found in …/transport-socket.lisp"
   #+end_example

   The form is present and loads fine; it is simply not matchable.

   Impact: such forms — and their leading comments/docstrings — cannot be
   edited structurally, forcing a fall-back to the generic text editor. Compounds
   with the comment-block issue above when a banner comment precedes a
   =define-alien-routine=.

   Suggested fix: extend the matcher so that when the element after =form_type=
   is a *list*, the name is resolved from the spec rather than skipping the
   form. For =define-alien-routine= the Lisp name is =(second name-spec)=. The
   same =(external internal)= shape appears in =define-alien-variable= and other
   =sb-alien= def-forms, so prefer a general "if the name position is a list,
   search it for the symbol matching =form_name=" rule over special-casing one
   macro.

   Note: both limitations were hit during ordinary doc/comment maintenance on a
   loaded, compiling system — not exotic input. Until fixed, the workaround is a
   plain-text edit followed by =lisp-check-parens= + =load-system= to prove
   structure was not disturbed.
* Parallel agent execution vs. ASDF system resolution
** TODO Worktree isolation does not isolate ASDF: a hotloading agent can resolve a worktree it does not own
   Running several editing agents concurrently against one repo is unsafe — they
   share one git working tree and one attached image, so branches collide and
   every cold verify is contaminated by another agent's in-flight edits. The
   standard remedy is to give each agent its own git worktree. For Common Lisp
   that remedy is incomplete, and the gap is quiet rather than loud.

   A worktree isolates the *filesystem*. ASDF's system namespace is *global* and
   keyed by system **name**, not by path. N worktrees of this repo are N
   directories each containing a =dsmr-mcp.asd= that all claim the name
   =dsmr-mcp=. Which one a given image loads is decided by source-registry
   search order, not by which worktree the agent was assigned. An agent can
   therefore compile, load, and test code it does not own, and report green — the
   same "a green certifies nothing" failure that worktrees were introduced to
   prevent, now harder to spot because the filesystem looks correctly isolated.

   Reproduction (the hazard is already in-tree, in two spots):

   #+begin_src lisp
   ;; src/hermetic/worker-client.lisp — inherited config is consulted FIRST,
   ;; and the explicit source is a :tree scan rather than a pinned directory.
   (asdf:initialize-source-registry
     '(:source-registry :inherit-configuration (:tree #p"...")))

   ;; src/bus/broker.lisp — the correct shape: explicit directory wins,
   ;; inherited config only fills in the remainder.
   (asdf:initialize-source-registry
     '(:source-registry (:directory #p"...") :inherit-configuration))
   #+end_src

   =src/lsp/client.lisp= repeats the worker-client form. With sibling worktrees
   under a scanned root, the =:tree= variant sweeps up every one of them, and the
   leading =:inherit-configuration= means anything resolvable from the global
   configuration outranks the source directory the worker was explicitly handed.

   Impact: blocks safe parallel agent execution, which is the actual goal. Today
   the only defensible posture is to serialize editing agents on a shared repo,
   which costs real throughput on every multi-plan piece of work. It also means
   the existing hermetic worker is less hermetic than its name claims — a
   pre-existing correctness question independent of parallelism. A related
   failure has already been observed with tree scans picking the wrong version of
   a dependency that ships many copies.

   Suggested fix:
   - Normalize every registry initialization to the broker's shape: the owned
     directory as an explicit =(:directory ...)= entry FIRST, =:inherit-configuration=
     last, and never =(:tree ...)= over a root that can contain sibling checkouts.
   - Give each parallel agent a source registry naming exactly the worktree it
     owns, so system-name resolution cannot reach a sibling regardless of what
     else is registered.
   - Keep worktrees out of any directory covered by an inherited tree scan
     (notably a local-projects tree), or they self-register and re-open the hole.
   - Give each agent its own fasl cache (=XDG_CACHE_HOME=); shared caches have
     already produced a flavor-mismatch crash here.
   - Then verify the property directly rather than assuming it: two agents, two
     worktrees, a deliberate divergence between them, and an assertion that each
     loads its own definition. Until that test exists, parallel Lisp execution
     should stay off.

* IPC Bus faults in practice (Burn Down)
** TODO the bus polling is too noisy, and an agents own bus emissions trip their own watches
   Update: the "own emissions" half is fixed. The wakeup watcher already filters a
   record carrying the agent's own encoded self-id, and =bus-status='s pending
   count now applies that same filter — it previously counted an agent's own
   un-consumed publishes, so status reported mail =bus-receive= would never hand
   back, read as loss. Count and delivery now share one foreign-record predicate
   (=envelope:foreign-record-p=) so they cannot drift apart again. Tracked in #48
   (fixed). The remaining half — poll cadence being too noisy — is unaddressed.

   Update 2026-07-26: the *volume* half of "too noisy" is fixed and measured. Both
   readers used to re-read and re-verify the whole log on every look; they now read
   only what was appended. Measured on a live 10-server / 10-watcher fleet: a server
   went from ~70% of a core and ~25 MB/s to 0.38-0.44% and ~2.7 KB/s, sustained
   across five hours of uptime; a watcher from ~43% and ~27 MB/s to 0.0-0.2% and
   ~1 KB/s. Shipped in #52.

   What is actually left under this heading is *cadence*, not volume, and it is now
   specific: the fleet does not agree on a poll interval. Four watchers run
   =--poll-ms 250= and five sit on the 1s default, so wake latency differs by 4x
   depending on which agent you are waiting for. Separately, arming a watcher still
   costs about one full WAL scan (7.7 MB measured against a 7 MB log; 15 MB for a
   fresh identity), paid again on every recycle and growing with the log — the fix
   bounded the poll, not the arm. Both belong to the wake-latency and rotation work.

** TODO agents fall into a trap where they send the wrong flags to re-arm the wakeup, resulting in:

  #+BEGIN_EXAMPLE
  [the captured output for this item was lost: a paste landed a tool
   invocation here instead of its result, and the file it pointed at
   (a scratch task log under /tmp) has since been reaped. Described
   from the known failure mode rather than reconstructed, because
   inventing plausible error text here would be worse than the gap.]

  Shape of the failure: dsmr-bus-watch treats an unrecognised flag as a
  hard exit. The wrapper loop restarts it, it exits again on the same
  bad flag, and nothing surfaces on the wake channel. The agent holds a
  watch it believes is armed while no process is listening, so a
  by-name dispatch never arrives and the silence is indistinguishable
  from an idle bus.
  #+END_EXAMPLE

  which effectively silences that agent until it is manually recovered by the operator, and becomes an attractor causing the problem to reoccur with increasing frequency. the only 'repair' seems to be dropping the context entirely by restarting the agent; /clear often doesn't heal the problem. /bus-watch is only a half fix for the operator to 'get us out of this hole', which only works reliably if context is purged, which is bad for lots of obvious reasons.

  Update: the deaf state is now *observable*, though not yet *prevented*. A watch
  writes a heartbeat while it runs; =dsmr-bus-watch --check-live= and
  =bus-status='s new =live_watcher= / =watcher_status= / =watcher_age_seconds=
  fields let an agent or a park routine detect that its own ears are off before
  the operator notices the latency. Tracked in #46 — observability shipped. The
  actual fix for this item — enforce the correct re-arm, or make persistent mode
  the default so wrong flags cannot silently deafen an agent — is the open
  residual of #46.

** DONE a delivered message showed no sender, so the name it was addressed to read as its byline
   CLOSED: 2026-07-26

   Messages were handed to a reader as their body alone. Bodies open with the name of
   the agent being *addressed*, so the first word read as a signature and readers
   credited messages to the wrong agent. It happened three times across the fleet in
   one day, twice to readers that were holding written warnings about it, and once by
   an agent that had just decoded the trap correctly for someone else and then laid it
   again in its own message.

   That last part is why this was worth fixing in code rather than in documentation:
   when a hazard keeps firing on people who know about it, the missing field is the
   defect and the care is not the remedy. The cost was real — four agents each spent a
   full measurement refuting a claim its supposed author never made.

   Receive now carries the publisher beside the body, as a field and as a labelled
   header. Same-project senders show a bare name; senders from another project are
   qualified by it, since two projects can each run an agent of the same name. A record
   that will not decode reads as "unknown" and is still delivered — naming the author
   must never become a condition of delivery. Shipped in #53.

   ⚠ Merged is not deployed: sessions keep the old render until the core is rebuilt
   and the servers restart.

* Build and deployment
** DONE rebuilding the core could fault every running server at once
   CLOSED: 2026-07-26

   A running server has the core file mapped for its whole life. =make core= wrote
   the new image directly over that path, so a routine rebuild while any server was
   up could fault all of them together. Nothing in the build enforced this. The only
   thing standing between the target and a downed fleet was the operator remembering
   to move the old image aside by hand first, which is a procedure, not a guarantee,
   and it had to be recalled correctly every single time.

   The build now writes to a staging path and renames the finished image into place.
   The rename installs a new file and leaves running servers holding the one they
   already mapped until each exits on its own schedule. A build that produces no
   image leaves the installed one untouched rather than replacing it with a
   fragment. The install path =install-bus-watch= uses was already correct; this
   brings the core target into line with it.

   The superseded image is kept rather than discarded, for two reasons. It is the
   rollback. It is also the only way a question about image size or dependency drift
   can be answered later: a roughly 20 MB swing between builds was unanswerable
   precisely because the previous image had been overwritten and no process still
   held it open.

   Verified against a live fleet rather than reasoned about: the rebuild landed at a
   fresh inode, all nine running servers kept their existing mappings and stayed
   asleep rather than faulting, no staging files were left behind, and the resulting
   image boots and serves its full verb set. Shipped in #54.

** TODO core image size varies by about 20 MB across builds with no input change
   Four builds of identical source with identical dependency manifests produced
   206.1 MB, 185.4 MB, 194.3 MB and 205.9 MB, swinging in both directions. The
   manifests were compared across the pairs and are the same, so this is not
   dependency drift, and it is not compression: the save call is unchanged, the
   string never appears in the build inputs anywhere in history, and the magnitude
   is wrong for it anyway, since a compressed image would land nearer a quarter of
   raw size rather than ninety percent of it.

   This is bounded rather than explained. The evidence says the variation is not
   symptomatic of anything, which is a different and much weaker claim than knowing
   what causes it. No mechanism has been identified.

   Impact is low but not nil: image size is one of the few cheap signals that a
   build went wrong, and a signal that moves 20 MB on its own cannot be read that
   way. Retaining each build's manifest and byte size alongside the previous image,
   which the staging change above now does as a side effect, is what makes the next
   occurrence diffable instead of unanswerable.
