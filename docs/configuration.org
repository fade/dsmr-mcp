#+TITLE: dsmr-mcp — Configuration
#+OPTIONS: toc:2 num:nil

This page is the operator reference for configuring a dsmr-mcp server: the
full environment-variable surface, how the dispatch mode and transport are
resolved, how the loopback bind is relaxed, how the filesystem sandbox is
scoped, and how to wire the server into an MCP client.

See also: [[file:index.org]] · [[file:installation.org]] · [[file:modes-and-transports.org]] ·
[[file:threat-model.org]] · [[file:operations.org]].

* Configuration precedence

Every server-startup knob resolves through one rule, in =src/run.lisp=:

#+begin_src text
keyword argument  >  DSMR_<NAME> env var  >  .dsmr-mcp.conf  >  built-in default
#+end_src

=.dsmr-mcp.conf= (at the project root) is read via =ubiquitous:value= and is
never written; its absence is silent. A conf key is the env name minus the
=DSMR_= prefix with underscores folded to dashes (e.g. =DSMR_LOG_LEVEL= ->
=:log-level=). A malformed value for a typed knob (transport, mode,
log-level, any port/seconds integer) raises =invalid-config-value= at
startup naming the offending variable. Only =:transport=, =:mode=, =:port=,
=:bind=, =:log-level=, and =:slynk-attach= participate in the conf layer;
the worker, LSP, HTTP, attach-concurrency, and sandbox knobs read the
environment (or their built-in default) directly.

* Environment variables

Exhaustive reference. =Read by= names the source file that consumes the
variable.

| Variable                       | Purpose                                                              | Default          | Read by                          |
|--------------------------------+---------------------------------------------------------------------+------------------+----------------------------------|
| =DSMR_TRANSPORT=               | Transport: =stdio= / =tcp= / =http=                                 | =stdio=          | =src/run.lisp=                     |
| =DSMR_MODE=                    | Dispatch mode: =attached= / =hermetic= / =auto=                     | =attached=       | =src/run.lisp=                     |
| =DSMR_SLYNK_ATTACH=            | =host:port= of the Slynk listener to attach to (attached mode)      | unset (nil)      | =src/run.lisp=                     |

| =DSMR_ALIVE_LSP_DIR=           | alive-lsp source checkout to spawn for LSP-backed verbs            | unset (attach-only) | =src/lsp/client.lisp=           |

| =DSMR_BUS_SELECTOR=            | Which [[file:bus-segmentation.org][bus]] this repo joins; unset means the shared host-wide bus | unset (via =.envrc=) | =src/bus/selector.lisp= |

| =DSMR_MCP_HOST=                | stdio<->TCP bridge target host (when =--host= is absent)          | =127.0.0.1=      | =scripts/stdio-tcp-bridge.lisp=    |
| =DSMR_MCP_PORT=                | stdio<->TCP bridge target port (when =--port= is absent)          | from argv        | =scripts/stdio-tcp-bridge.lisp=    |
| =DSMR_CORE_OUTPUT=             | Output path for the prebuilt core image (=make core=)             | =dsmr.core=      | =scripts/build-core.lisp=          |

=DSMR_ALLOW_REMOTE= is true only for the literal values =1=, =true=, or
=yes=. =DSMR_RELATED_PROJECTS= is consulted at re-root time inside the
filesystem sandbox — *not* in =src/run.lisp='s startup config (see
[[Filesystem sandbox]]).

** Worker-internal variables (not operator knobs)

The dispatcher sets these on each hermetic worker child; do not set them
yourself: =DSMR_WORKER_SECRET= (128-bit auth handshake), =DSMR_WORKER_ID=,
=DSMR_PARENT_PID=, =DSMR_WORKER_SWANK= (optional in-worker Slynk),
=DSMR_WORKER_EVAL_TIMEOUT=, and =DSMR_NO_WORKER_POOL= (guards a worker from
spawning its own pool). They are documented here only so they are not
mistaken for configuration.

* direnv per-project setup

A single global =~/.claude.json= dsmr-mcp entry can carry only one
=DSMR_SLYNK_ATTACH=, so it cannot serve several Lisp projects at once —
each with its own image and Slynk port. A per-project =.envrc= (managed by
[[https://direnv.net][direnv]]) fixes this: it supplies the attach target and the
related knobs *per project*, exported into the environment when you launch
your agent from that project's directory. The dsmr-mcp server inherits those
variables and drives *that* project's image, which lets the global MCP entry
stay env-free and canonical instead of hardcoding one project's listener.

** The shipped =.envrc=

The template dsmr-mcp puts into position is copied verbatim — it uses shell
=${VAR:-default}= expansion, so no per-project rendering is needed:

#+begin_src bash
# .envrc — dsmr-mcp per-project configuration (direnv). Run `direnv allow` to activate.
# These DSMR_* vars are inherited by the dsmr-mcp MCP server when you launch your
# agent (e.g. `claude`) from this directory — so the server drives THIS project's
# image without hardcoding anything in your global ~/.claude.json.

export LISP_WORKSPACE="${LISP_WORKSPACE:-$HOME/SourceCode/lisp/}"

# This project's Slynk listener. scripts/dev-boot.sh reads the same two vars,
# so dev-boot and dsmr-mcp stay in sync (single source of truth).
export SLYNK_HOST="${SLYNK_HOST:-127.0.0.1}"
export SLYNK_PORT="${SLYNK_PORT:-4005}"

# auto = attach to the image above if reachable, else a private hermetic worker.
export DSMR_MODE=auto
export DSMR_SLYNK_ATTACH="${SLYNK_HOST}:${SLYNK_PORT}"
export DSMR_LOG_LEVEL=info

# This project's stable bus identity. The dsmr-mcp coordination bus uses it so
# this project's main agent resumes its durable message cursor across restarts
# instead of getting a fresh ephemeral id every launch. Defaults to the project
# directory name; override by exporting DSMR_BUS_AGENT before direnv loads.
export DSMR_BUS_AGENT="${DSMR_BUS_AGENT:-$(basename "$PWD")}"

# The fleet this project's agent belongs to. An empty value means the shared
# host-wide bus, so a repository that gains this line has not moved anywhere.
# Set it to the fleet tag the leader named to join that fleet's private bus.
export DSMR_BUS_SELECTOR="${DSMR_BUS_SELECTOR:-}"

# Whether this project's agent may publish to one named recipient instead of
# broadcasting to every participant. On, so this project can answer whoever
# asked it, by name, from its first run; export DSMR_BUS_DIRECT_ADDRESSING=0
# before direnv loads to go back to broadcast only.
export DSMR_BUS_DIRECT_ADDRESSING="${DSMR_BUS_DIRECT_ADDRESSING:-1}"

# Sibling projects this one may re-root into (filesystem sandbox whitelist):
# export DSMR_RELATED_PROJECTS="$HOME/SourceCode/lisp/cl-mcp:$HOME/SourceCode/lisp/eve-quant"
#+end_src

The attach target is *derived*: =DSMR_SLYNK_ATTACH="${SLYNK_HOST}:${SLYNK_PORT}"=
is built from the same two variables that =scripts/dev-boot.sh= reads to start
the project's listener, so the listener you boot and the target dsmr-mcp
attaches to are a single source of truth and cannot drift. =DSMR_MODE=auto=
means the server attaches to that image when it is reachable and otherwise
spins up a private hermetic worker, so the =.envrc= works whether or not your
project image is running.

The =DSMR_BUS_AGENT= line gives this project a stable identity on the
[[file:coordination-bus.org][agent coordination bus]], defaulting to the project
directory name. With it set, the project's main agent resumes its durable message
cursor across restarts instead of taking a fresh ephemeral identity each launch.
It is harmless if you never use the bus.

⚠ The =:-= fallback only applies when the variable is *unset*. A shell that has
already exported another project's =DSMR_BUS_AGENT= passes it straight through,
and this project's agent comes up under a name that is already taken, eating the
other agent's mail. If you launch agents from a shell that has sourced another
repository's environment, pin the name literally rather than deriving it.

The =DSMR_BUS_SELECTOR= line names which [[file:bus-segmentation.org][bus]] this
repository joins. It ships *empty*, which means the shared host-wide bus, so
adding the stanza everywhere puts nobody on anybody else's bus; a fleet moves
only when its tag is filled in. The MCP session and any watcher armed from this
directory read the same variable, which is what keeps them on one bus instead of
drifting apart while both report success.

The =DSMR_BUS_DIRECT_ADDRESSING= line decides whether this repository's agent
may publish to one named recipient. The capability is off in the code, so a
repository whose =.envrc= does not carry the line has it off: naming a recipient
publishes nothing and returns an error. The line ships set to =1= because the
half-enabled state is the expensive one. A leader can address a worker while the
worker cannot answer by name, so every answer becomes a broadcast and a question
put to one repository is answered by all of them. Export
=DSMR_BUS_DIRECT_ADDRESSING=0= before direnv loads for broadcast only.

⚠ Naming a recipient filters *delivery*, not *readership*. The record still
travels on the fleet's shared log and any member can read it there.

⚠ Editing =.envrc= is not enough on its own: run =direnv allow .= afterwards, and
remember that an MCP server already running keeps the environment it started
with until it is restarted or the client reconnects. Either omission leaves the
session on the shared bus while a watcher armed with an explicit =--bus= listens
on the named one, with both sides reporting healthy.

** How the =.envrc= gets into place

There are three ways a project ends up with this file, depending on how you
start:

- *Greenfield (scaffold).* When you stand up a new project with the scaffold,
  the =.envrc= is emitted automatically as part of the generated file set —
  scaffolding the project *is* the consent to write it.
- *An existing Lisp project.* When dsmr-mcp runs in a project that already has
  an =*.asd= file but no =.envrc=, it *asks* before writing one. On your first
  dsmr-mcp tool use in that session, the server raises a native yes/no consent
  dialog in the client; only on an explicit accept does it write the =.envrc=,
  and it writes through the same filesystem write-jail every other tool obeys.
  An existing =.envrc= is *never* clobbered, and you are asked at most once per
  session — a decline is remembered for the rest of the session. The prompt
  only appears with clients that support MCP elicitation and the stdio
  transport; with any other client it is a silent no-op, never an error.
- *An existing =.envrc= missing the dsmr-mcp setup.* If your project already has
  an =.envrc= — one you wrote by hand, or one from another tool — but it does not
  export the dsmr-mcp variables, the server offers to *append* them rather than
  leave the project unconfigured. On accept, a clearly marked block (delimited by
  =# >>> dsmr-mcp ... >>>= / =# <<< dsmr-mcp <<<= comments) is added to the *end*
  of the file; your own lines are untouched, and you can edit or delete the block
  freely. You will need to run =direnv allow= again afterward. A file that
  already exports the dsmr-mcp setup is recognised as complete and is never
  re-prompted, so the offer appears at most once and never twice for the same
  file.
- *Site-wide defaults (installer).* The installer offers to write a
  personalized template to =~/.config/dsmr-mcp/envrc.template= (default Slynk
  host/port, =LISP_WORKSPACE=, mode, log level, related projects). Both paths
  above prefer that site template when it exists and fall back to the shipped
  default otherwise, so every project you create starts from *your* defaults.
  Pass =--no-envrc-defaults= to the installer to skip the offer; in a
  non-interactive install it is a silent no-op and writes nothing.

** Activating the file: =direnv allow .=

direnv will not load a new or changed =.envrc= until you authorize it — this is
direnv's trust model, and it is deliberate. After the file is created or
edited, review it and run:

#+begin_src sh
direnv allow .
#+end_src

Until you do, the variables are not exported and dsmr-mcp sees none of them.
dsmr-mcp does *not* require direnv to be installed: the =.envrc= is an inert
text file without it, and the server falls back to its normal configuration
sources ([[Configuration precedence]]). direnv is simply the most ergonomic way to
scope these variables to a project directory.

* Mode selection

=DSMR_MODE= chooses how dsmr-mcp obtains a Lisp image to drive:

- =attached= (default) — connect to a user-supplied Slynk listener at
  =DSMR_SLYNK_ATTACH= and operate inside that running image. An explicit
  =attached= *never* falls back to hermetic: a dead listener fails closed
  with a structured error, not a silent swap.
- =hermetic= — spawn private, dsmr-mcp-owned SBCL worker processes (one per
  session); the server never touches a user image.
- =auto= — resolve at startup by probing the Slynk listener at
  =DSMR_SLYNK_ATTACH= (a 3-second TCP connect): reachable collapses to
  =attached=, unreachable collapses to =hermetic= and logs a one-time
  startup warning. =auto= is the explicit opt-in for that logged fallback;
  it is not the default.

Resolution order is keyword =:mode= > =DSMR_MODE= > =.dsmr-mcp.conf= >
=attached=. The =auto= probe runs only after the stderr log appender is
installed, so the warning never lands on the stdout JSON-RPC channel. See
[[file:modes-and-transports.org]] for the operational trade-offs.

* Transport selection

=DSMR_TRANSPORT= selects how MCP clients reach the server:

- =stdio= (default) — JSON-RPC over stdin/stdout, one message per line.
  This is the path MCP clients launch directly as a child process, and the
  recommended configuration for Claude Code and similar agents.
- =tcp= — newline-framed JSON-RPC on a socket at =DSMR_BIND:DSMR_PORT=,
  one session per connection.
- =http= — Streamable HTTP (MCP 2025-03-26 / 2025-06-18) over Hunchentoot
  at =DSMR_BIND:DSMR_PORT=, for clients that speak the HTTP transport.

Resolution order mirrors mode: keyword > =DSMR_TRANSPORT= > conf > =stdio=.

** Bind address and loopback default

Both networked transports bind to loopback (=127.0.0.1=) by default. Before
any listener socket is created, =%check-remote-bind= refuses a non-loopback
=DSMR_BIND= (anything other than =127.0.0.1=, =::1=, or =localhost=) unless
=DSMR_ALLOW_REMOTE= is set to =1=, =true=, or =yes= — a refused bind raises
=invalid-config-value= naming =DSMR_BIND=.

#+begin_src sh
# Loopback only (default):
DSMR_TRANSPORT=tcp DSMR_PORT=7878 dsmr-mcp

# Bind a routable interface — operator opt-in, no built-in auth (see safety note):
DSMR_TRANSPORT=tcp DSMR_ALLOW_REMOTE=1 DSMR_BIND=0.0.0.0 DSMR_PORT=7878 dsmr-mcp
#+end_src

*Safety note.* =DSMR_ALLOW_REMOTE= is an explicit operator decision to
expose the server beyond the local host. It only removes the loopback
restriction — it adds *no authentication and no TLS*. A remotely reachable
server grants its full tool surface (arbitrary REPL eval, filesystem
reads/writes within the sandbox) to anyone who can reach the port.
First-class auth/TLS is a v2 item. If you must expose it, front it with an
authenticating reverse proxy or an SSH tunnel and restrict the network
path. See [[file:threat-model.org]] for the full risk discussion.

For clients that can only spawn a stdio subprocess but need to reach a TCP
server, a bundled =stdio<->TCP= bridge (=DSMR_BRIDGE_HOST= /
=DSMR_BRIDGE_PORT=) pumps bytes between the two; see
[[file:modes-and-transports.org]].

* Filesystem sandbox

dsmr-mcp confines filesystem-touching tools to a session-scoped project
root rather than a global one.

- *Session project root.* The write/edit jail is the current session's
  project root. It starts unset and is established with the
  =fs-set-project-root= tool; an fs verb invoked before a root is set fails
  with =project-root-not-set-error= rather than silently using the cwd.
  (=DSMR_PROJECT_ROOT= seeds the server's startup working root and the conf
  reader, but the per-session sandbox root is what the fs verbs enforce.)
- *Re-root whitelist (=DSMR_RELATED_PROJECTS=).* A colon-separated list of
  absolute directories (PATH-style) the session may re-root *into* without
  human approval. It is parsed at re-root time in
  =src/tools/fs-set-project-root.lisp=, not captured by =src/run.lisp='s
  startup config. A re-root target outside both the current root and the
  whitelist is denied and requires =human_approved: true= on the
  =fs-set-project-root= call — and an autonomous agent cannot self-approve;
  the violation raises =reroot-permission-required-error=.
- *Read passthrough.* Reads are broader than writes: source under
  registered ASDF source directories (sibling and dependency checkouts) is
  readable, read-only, so code-intelligence verbs can follow definitions
  into libraries even when those paths fall outside the write jail.

#+begin_src sh
# Permit re-rooting into two sibling checkouts without per-call approval:
export DSMR_RELATED_PROJECTS="/home/me/SourceCode/lisp/cl-mcp:/home/me/SourceCode/lisp/eve-quant"
#+end_src

See [[file:threat-model.org]] for the re-root approval gate, the symlink-escape
closure, the broad-root deny list, and the read-vs-write boundary in detail.

* Wiring dsmr-mcp into an MCP client

dsmr-mcp is itself an MCP server. The recommended transport for agent
clients is =stdio=: the client launches dsmr-mcp as a child process and
talks JSON-RPC over the pipe.

** Claude Code

Register the server under =mcpServers= in =~/.claude.json= (it coexists
with other servers such as cl-mcp):

#+begin_src json
{
  "mcpServers": {
    "dsmr-mcp": {
      "command": "dsmr-mcp",
      "args": [],
      "env": {
        "DSMR_MODE": "auto",
        "DSMR_TRANSPORT": "stdio"
      }
    }
  }
}
#+end_src

** Other agents

Any MCP-capable agent launches dsmr-mcp the same way: invoke the =dsmr-mcp=
entry point with =DSMR_TRANSPORT=stdio= and pass per-server environment
through the client's own server-config block. For clients that prefer a
socket, run a =tcp= (or =http=) transport instance and point the client at
=DSMR_BIND:DSMR_PORT= (loopback unless =DSMR_ALLOW_REMOTE= is set).

** Automated install / configure helper

The bundled installer automates this wiring end to end: it writes the
=mcpServers= block into =~/.claude.json= (backing the file up and
re-parsing the result before committing the write), copies the
=scaffold-project= skill into =~/.claude/skills/=, and handles an existing
cl-mcp entry so the two can coexist or dsmr-mcp can take over — no
hand-editing JSON. Prefer it over manual edits: it keeps the env defaults
and command path consistent with the installed build.

Run it from the checkout:

#+begin_src sh
sbcl --script scripts/install.lisp [FLAGS]
#+end_src

| Flag                  | Effect                                                              |
|-----------------------+---------------------------------------------------------------------|
| =--keep=              | Coexist with any existing cl-mcp entry (the default)                |
| =--migrate=           | Remove an existing cl-mcp entry, install dsmr-mcp                   |
| =--replace=           | Replace an existing cl-mcp entry with dsmr-mcp                      |
| =--print=             | Print the canonical JSON snippet to stdout instead of writing =~/.claude.json= (for non-Claude agents) |
| =--no-skill=          | Do not copy the scaffold skill into =~/.claude/skills/=             |
| =--no-envrc-defaults= | Skip the interactive site-wide =.envrc= defaults step (otherwise offered after the install when stdin is a tty) |

=--keep= / =--migrate= / =--replace= are mutually exclusive; the last one
wins. The manual =~/.claude.json= block above remains a supported
fallback. See [[file:installation.org]] for build and install steps.

** Scaffolding a new project

The =scaffold-project= skill (copied into =~/.claude/skills/= by the
installer unless =--no-skill= was passed) stands up a new Common Lisp
project from the dsmr-mcp skeleton when invoked in an empty directory: a
package-inferred ASDF system, packages, a zebra smoke test,
delivery-discipline files, and the per-project =.envrc= described above.
The same generation is reachable directly as the =project-scaffold= MCP
verb — see the [[file:tools.org][tool reference]] for its schema.
