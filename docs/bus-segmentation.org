#+TITLE: dsmr-mcp - Bus segmentation
#+OPTIONS: toc:2 num:nil

This document answers a single question: when several unrelated projects each
have live agents on one workstation, how should the coordination bus keep them
out of each other's traffic?

It states where things stand today (measured, not estimated), the two candidate
designs and why one was chosen over the other, the failure mode that should
drive the acceptance criteria, the surface as it was actually built, and the
adoption path. For how the bus works at all, read [[file:coordination-bus.org][Agent coordination bus]] first;
this document assumes it.

Measurements below were taken on 2026-07-27 unless stated otherwise. Numbers in
this document are stamped because a figure without its expiry condition outlives
the thing it described.

* The situation is present tense

The bus is one host-wide instance. There is a single write-ahead log, a single
broker lock, a single membership file, and a single pair of sockets for the
whole workstation.

The namespace that already exists scopes *identity*, not *delivery*. A cursor is
keyed on =<project-root>/<name>=, so an agent never re-reads a message it has
already consumed, and it never receives its own publishes back. But every
message from every project still lands in the one log, and every reader still
walks past it.

That is no longer hypothetical. Counting distinct project roots in the live
cursor population:

| Project root                     | Cursors |
|----------------------------------+---------|
| a constellation of eight repos   |     173 |
| dsmr-mcp                         |      15 |
| an unrelated TLS project         |       4 |
| a vendored test library checkout |       2 |
| ephemeral subagents under /tmp   |      16 |

Four real projects share one 7.27 MB log. Two of them have no reason ever to see
the constellation's traffic, and currently see all of it.

* The unit of isolation is a fleet, not a project

The obvious move is to derive the bus from the project root, so each project
gets its own. That is wrong, and it is worth being explicit about why, because
it looks correct until it breaks the thing the bus is for.

The eight-repo constellation is eight *separate project roots* whose agents must
reach each other. That cross-repo delivery is the bus's main job. Deriving the
bus from the working directory would sever it, giving eight isolated buses with
one agent each and no way to coordinate.

So the boundary is a *fleet*: a named group of cooperating agents that may span
any number of repositories. A fleet is declared, not inferred. One project can
belong to a fleet with seven others, or sit alone.

* Two candidate designs

** Rejected: filter delivery on a shared log

Keep one log, and have each reader skip records whose namespace does not match
its own.

This is cheap to build and it is not isolation. Foreign traffic still reaches
disk, still occupies the log, and still has to be read and discarded by every
reader. The log stays a single contention point that grows at the sum of every
project's rate, and the cost of one noisy fleet is paid by every quiet one.

It also fails the property that actually matters operationally: a fleet cannot
be reasoned about, archived, or retired independently, because its history is
interleaved with everyone else's in one file.

One distinction has to be drawn here, because the bus as built does filter
delivery in one place and that looks at first like the design just rejected. A
message may name a single recipient, and every other reader filters it out. The
difference is volume. Separating fleets was about not carrying another fleet's
traffic at all: foreign records reaching your disk, growing your log, and being
read and discarded by you at your expense. Within one fleet every member already
carries every message, because that is what a fleet is. Filtering there changes
only who reads a record, never what reaches disk, so the argument above has
nothing to say about it.

** Chosen: a selector that resolves to a separate state root

A named selector resolves to a state root. Unset means today's host-wide bus,
byte for byte. Set means a private root with its own log, broker lock,
membership file, cursor directory, and socket pair.

Most of the plumbing for this already existed: the path derivation takes a root
and derives every path under it, and brokers already elect per root. What was
missing was that nothing in the tree ever passed a non-default root.

Three properties make this the better trade:

- *Real isolation.* A foreign fleet's traffic never touches your disk, never
  enters your log, and cannot be read by you at all.
- *Opt-in.* An unset selector is the current behaviour exactly, so nothing
  multiplies until someone chooses it, and there is no migration step.
- *Independent lifecycle.* Each fleet's log can rotate, archive, and be reasoned
  about on its own.

The selector is a human-friendly name and is bounds-checked. The path it derives
is that name verbatim, so the state directory stays legible to anyone reading it
by hand. A Unix domain socket path is limited to roughly 108 bytes, and the
answer to that is to bound the name and refuse one that will not fit, rather
than contorting the path into something opaque.

Selection precedence mirrors the existing identity resolution rather than
introducing a second mental model for one concept.

* The failure mode that should drive acceptance

=dsmr-bus-watch= is a separately built and separately deployed binary. It
derives the bus state root *itself*, with its own copy of the derivation, and
deliberately does not depend on the broker module, because that dependency would
pull ZeroMQ into the watcher binary.

So there are two independent derivations of the same path. A selector has to
reach both.

If the watcher does not learn the selector, it arms on the wrong bus and *never
fires*. It does not error. It reports healthy. An agent in that state is deaf
while believing itself armed, and the condition is discovered only when somebody
notices that a message was never answered.

The liveness probe cannot currently distinguish this, because it answers only
whether a watcher is alive, and a watcher on the wrong bus is perfectly alive.

*Therefore, as an acceptance criterion rather than a nicety: the liveness probe
and the status verb must both report which bus they are attached to, not merely
whether they are attached.* That single change makes the entire class visible at
a glance, and it is cheap next to the cost of not having it.

A second consequence to state deliberately rather than discover: the restart
listener becomes bus-scoped. A leader on one bus can no longer reach a project
on another, by construction. Isolation is the feature, so this is intended, but
it is a real reduction in reach and should be a decision rather than a surprise.

An operator-facing global restart therefore *cannot ride the bus*. It has to
enumerate the bus roots on disk and act out of band, writing its state to files
per root. It is a filesystem operation, not a bus message.

* The surface as built

This section describes what exists rather than what was proposed. The acceptance
criterion above is met: every liveness answer names the bus it answers for.

** A name resolves to a state root

A bus name is one literal directory segment. The unnamed bus is the path the bus
has always used, and a bus called =valis= is that same path plus a =valis/=
segment. Everything else derives from there and nowhere else: the log, the
broker lock, the membership file, the cursor directory, the roster, and the pair
of sockets. One function performs that derivation, and the broker, the watcher
binary and the liveness beat all reach it, so the two copies the previous
section warned about are now one.

A name is bounded at 32 characters, restricted to letters, digits, hyphen,
underscore and dot, and refused if it collides with something the state
directory already means, =cursors= and =members= among them. The socket path the
name would derive is measured against the kernel's limit at that moment, and a
name that will not fit is refused outright. Nothing is ever shortened to make it
fit, because a truncated socket path is a silently different bus, which is the
whole class of failure this work exists to close.

** How the selector is set, and how it is inherited

One variable, =DSMR_BUS_SELECTOR=, declared in a repository's =.envrc= beside the
agent name. Every process started in that repository inherits it, so an MCP
session and a watcher armed from the same shell cannot land on different buses
while both report themselves healthy. An empty value means the unnamed bus,
which is what an untagged repository keeps getting.

Precedence mirrors the identity resolution that already existed rather than
introducing a second model for one idea: an explicit argument wins, then the
environment variable, then the unnamed bus. Each bus verb takes an optional bus
argument for a one-off, and each reports back which bus it acted on, printing
=default= for the unnamed one. A name that cannot become a bus is refused, and
nothing is ever published to, read from, or reported on the shared bus in place
of a bus that was named. Silently landing on the wrong bus is the failure worth
paying to avoid, so the refusal is loud and total.

** What a watcher reports

The watcher takes =--bus=, defaulting to the same variable the =.envrc= declares
and the session resolves through. It validates the name where the operator's
value is read and refuses to start on an unusable one: a mistyped cadence flag
costs its own default, but a bus name that quietly degraded to the default would
leave a watch armed where nobody is talking, reporting live and never firing.

The liveness probe names the bus on every answer, the unnamed bus included,
where it prints =default=. A field that appeared only for a named bus could not
tell a watcher on the default bus from a binary too old to know that buses have
names, which is the same silence the field exists to break. =default= can only
ever mean the unnamed bus, because the bus refuses it as a name.

One watch is armed per bus an agent is on. An agent may be on more than one: it
holds a connection, a membership and a cursor on each, which is how an agent
reports into a neighbouring fleet without carrying that fleet's traffic
everywhere else. That is opt-in by definition, and the cost of the traffic it
does carry was chosen.

** What the roster holds, and what it does not

Each bus has a roster held by its own broker under its own root: who is
enrolled, who leads the bus, whether enrollment is open, and, for anyone who has
left, the time they left. It is a different thing from the membership file one
directory up, which is the lock live processes hold and which dies with them.

The roster is operator-managed and *advisory*. Nothing on the serving path
consults it. An agent absent from the roster, or refused a place on it, still
connects, still publishes and still receives exactly as any other participant.
Closing enrollment stops a leader listing new participants and stops nothing
else: it is a gate, not an access control list.

That is deliberate. Isolation between fleets comes from the separate state root
and the filesystem permissions on it, never from a membership check, because the
transport has no security surface that could back one. A declared leader plus a
closeable gate is the whole answer to two fleets sharing a machine: each names
its own bus and records its own leader. Adding a cryptographic guard here would
dress a convention up as a control.

** What leaving does

An agent that leaves cleanly reads out whatever is still waiting for it, records
its departure on the roster with the time, and disconnects. That entry transfers
custody of its cursor to the bus's broker, which from then on keeps the cursor
at the head of the log and retires it once the departure is old enough.

Two things follow, and both are the point. A departed participant can never pin
the log with records it will never read, so the pathology of one stale cursor
holding weeks of log against retention cannot arise for an agent that left
properly. And holding a cursor never quietly becomes keeping it forever, because
what ages it out is the recorded departure time and not the file's own
modification time: a held cursor is written continuously, so its modification
time is always within seconds of now.

Returning later resumes at the current head. No backlog arrives for the time
away, which is what having left means rather than a loss of mail. Leaving twice
is safe and does not push the departure time forward. Leaving does *not* rotate
the log: rotation still needs every member gone and then the broker stopped, and
a departing agent cannot reach that trigger on its own.

** What addressing promises, and what it does not

A message may name one recipient, and delivery hands it to that recipient alone.
The record itself is ordinary: it sits in the fleet's one log like any other,
and every reader's cursor still advances past it. A reader that stalled on mail
addressed to somebody else would become exactly the log pin that holding cursors
exists to prevent, so the filter is at delivery and never at the cursor.

This is a delivery convenience, not a privacy boundary. The record is on the
fleet's disk and readable by anyone who can read the fleet's state root. Claiming
otherwise would be the same mistake as a bus-enforced roster.

The path is built and off by default. The traffic pattern actually in use is
leader to member and member to leader, which needs no addressing at all, and the
capability exists because a bus that knows its participants' identities can
address them, not because the pattern in use asked for it.

* Using a named bus

Everything above describes the design. This section is the operating procedure:
what to type, what to expect back, and which of the answers are lying to you.

** Put a fleet on a bus of its own

The bus name is one variable in each participating repository's =.envrc=, beside
the agent name:

#+begin_src sh
export DSMR_BUS_AGENT="${DSMR_BUS_AGENT:-my-repo}"
export DSMR_BUS_SELECTOR="${DSMR_BUS_SELECTOR:-valis}"
#+end_src

⚠ A =.envrc= that has been edited does not take effect until it is allowed
again. Run =direnv allow .= in the repository afterwards. Until you do, the
variable is absent, every process falls back to the shared bus, and nothing
reports an error, because falling back is a legitimate configuration.

⚠ Prefer a literal default to =$(basename "$PWD")=. The =:-= fallback only
applies when the variable is unset, so a shell that already exported another
repository's identity passes it straight through and the agent comes up under a
name that is already taken, quietly eating that agent's mail.

** Bringing a fleet up on a bus that already exists

The common case after the first day: the bus has been running for weeks, it holds
history and cursors, and you are starting agents against it again. The thing to
know before anything else:

⛔ *A running bus is not an assembled fleet, and starting the agents does not
assemble one.* These are three separate facts, and each can be true without the
others:

1. the bus exists and its broker is serving;
2. the agents are running and can reach it;
3. a roster records who is in the fleet and who leads it.

Starting an agent in each repository gets you 1 and 2. It does not get you 3.
Neither =/leader= nor =/worker= enrolls anybody: they rebuild an agent's own
context and arm its watch. Enrollment is =/fleet='s job and only =/fleet='s. A
fleet brought up without it works, publishes and receives perfectly well, and has
no record of who is in it.

*The order that works:*

1. *Assign the tag* in each participating repository's =.envrc=, then
   =direnv allow .= in each. Do this before starting any agent, because a process
   inherits the environment it was started with.
2. *Start the agents*, one per repository.
3. *Run =/fleet=* from the leader's terminal to declare the leader, enroll each
   sister, and close enrollment. This is the step that is easy to skip, because
   everything already appears to work without it.
4. *Each sister arms its watch* and proves it with a wrong-namespace control.

*Check what you are joining before you assemble.* On a bus with history, ask what
is already there:

#+begin_src sh
scripts/bus-inspect.sh --list          # which buses exist
scripts/bus-inspect.sh <bus>           # broker, roster, cursors for one
#+end_src

⚠ *An empty roster and a bus that never had one print the same line*: no entries,
enrollment open, leader none. On disk they differ, because a roster that has ever
been written carries an =updated-at= stamp and a synthesized empty one does not.
If the distinction matters, read the stamp rather than the summary. A roster file
that was deleted outright is indistinguishable from one that never existed.

*What returning agents do with the history.* Cursors are durable and survive
everything above, so an agent that has been away resumes at its own cursor and
may wake to a backlog rather than to silence. An agent that left through
=bus-leave= is different: the busmaster held its cursor at the head, so it returns
to the current head and is delivered nothing from the period it was away. Neither
is a fault, but they look very different on the first wake, so know which one you
are watching.

*Confirming the bring-up.* Two questions, and they are not the same question:

- *Who is in the fleet?* The roster answers, and it is a record of intent.
- *Who can actually hear?* Only =--check-live= answers, per agent, per bus.

⛔ Never read enrollment as reachability. An enrolled agent whose watch is dead is
silent, and an unenrolled agent receives everything normally. A bring-up is
finished when every sister answers =live= on the bus you meant, not when the
roster looks complete.

** Find out which bus you are actually on

Two sides resolve the bus independently, and they can disagree. Ask each.

The session, through any bus verb, which reports the bus it acted on:

#+begin_src
bus-status
  => You are "my-repo" ... Bus valis is up: 0 message(s) pending.
#+end_src

The watcher, through its liveness probe:

#+begin_src sh
dsmr-bus-watch --check-live --bus valis \
  --agent "$DSMR_BUS_AGENT" --namespace "$(pwd -P)/"
#+end_src

⚠ If those two name different buses you are *split*: the session talks on one
bus and the watch listens on another, and both report themselves healthy. This
is what an unallowed =.envrc= produces, and what a server that started before the
variable existed keeps producing until it is restarted or the client reconnects.
Fix the environment on both sides. Passing =--bus= to the watcher alone papers
over it and leaves every verb that forgets the argument on the wrong bus.

** Arm a watch, and prove it is the right one

Arm the loop rather than the bare watcher, one per bus:

#+begin_src sh
while true; do
  dsmr-bus-watch --stream --poll-ms 250 --recycle-seconds 1800 \
    --bus valis --agent "$DSMR_BUS_AGENT" --namespace "$(pwd -P)/"
done | grep --line-buffered -E "^(bus|error):"
#+end_src

=--stream= exits 0 on its idle window on purpose: that is the self-heal that
re-arms a watch which has gone silently deaf. The loop turns that exit into a
re-arm. A bare =dsmr-bus-watch --stream= goes deaf at the first idle mark while
still believing it is armed.

⛔ =--namespace= takes the absolute project root with its trailing separator, not
the repository's name. Paste =pwd -P=. The cursor and the heartbeat are both keyed
on =<namespace>/<name>=, which produces the trap below.

⚠ *A wrong namespace confirms itself.* A watch armed under the wrong namespace
writes its heartbeat there, and a probe passing the same wrong namespace reads
that heartbeat back and answers =live=. The check agrees with the mistake. So
prove it with a control that must fail:

#+begin_src sh
dsmr-bus-watch --check-live --bus valis \
  --agent "$DSMR_BUS_AGENT" --namespace /nonexistent/
  => dead bus=valis          # required. `live` here means you are reading
                             # your own misfiled heartbeat.
#+end_src

** Reading the liveness answer

Every answer names its bus, on every outcome, so a watcher that is live on the
wrong bus is readable rather than invisible.

| Answer                            | Exit | Means                                          |
|-----------------------------------+------+------------------------------------------------|
| =live pid=N age_s=n bus=valis=    |    0 | Listening, on the bus you asked for            |
| =live ... bus=<other>=            |    0 | *Deaf.* Live on a bus nobody is talking on     |
| =live ... bus=default=            |    0 | On the shared host-wide bus                    |
| =dead bus=valis=                  |    1 | Nothing listening. Re-arm                      |
| =stale pid=N ...=                 |    1 | A watch existed and stopped refreshing         |
| no =bus== field at all            |    - | Binary predates named buses. Reinstall it      |
| refusal message                   |   64 | The name was rejected. Nothing was armed       |

=default= is unambiguous: it can only ever mean the shared bus, because the bus
refuses =default= as a name.

** Names the bus will refuse

A name is one directory segment: at most 32 characters of letters, digits,
hyphen, underscore and dot. Reserved names the state directory already uses, such
as =cursors=, =members= and =default=, are refused, as is any name whose derived
socket path would exceed the kernel's limit.

Refusal is always outright, and exits 64. Nothing is shortened to fit and nothing
falls back to the shared bus, because a truncated or downgraded name is a
silently different bus, which is the entire failure class this exists to close.

#+begin_src sh
dsmr-bus-watch --check-live --bus cursors ...
  => refusing the bus name "cursors". That name is reserved ...  # exit 64
#+end_src

** Inspecting a bus on disk

=scripts/bus-inspect.sh= reads a bus's state without composing paths by hand:
=--list= for the buses that exist, a bare =[BUS]= for one bus's state, and
=--id PATH NAME= to compose an agent id.

** What isolation does and does not give you

Separate buses give separate state roots, so traffic does not cross and one
fleet's broker dying does not touch another's. Isolation comes from that
separation and the filesystem permissions on it.

It does *not* come from the roster. The roster is advisory: nothing on the
serving path consults it, an agent absent from it still publishes and receives
normally, and closing enrollment only stops a leader listing new participants.
Being on the roster is not evidence of being connected, and =--check-live= is.

* Two recent findings that bear on sequencing

** The cursor reaper is not broken

The reaper had appeared not to run: cursor files accumulated for weeks while the
reaping code inspected as correct.

On 2026-07-27 a deliberately restarted broker logged that it reaped 185 orphaned
ephemeral cursors older than seven days, taking the directory from 394 files to
209. The reap runs at broker startup. A broker that has been up for six days
never reaches that path again, which is a sufficient explanation for unbounded
growth without any defect in the reaper itself.

Bound, since closed: one observation of a reap at startup did not prove there
was no separate periodic path that was independently broken. Reading the call
site settled it. The reap has exactly one call site, inside broker startup, and
no timer and no second thread anywhere reaches it, so startup-only is now
established rather than inferred.

** Small buses make log rotation reachable

Rotation is currently gated on the last member leaving cleanly, which was
confirmed by measurement: while a fleet is up, the exclusive upgrade of the
membership lock is refused, so the trigger is never reached. A constellation
that never disperses never rotates.

This cuts both ways for segmentation, and the second direction is easy to miss.
Segmentation multiplies the number of logs and cursor directories, so an
unreachable rotation trigger becomes a problem in more places. But a small fleet
that genuinely parks at the end of a working session *does* reach last-member-out
and rotates cleanly. Segmentation therefore partially repairs the trigger rather
than only multiplying the problem.

* Adoption path

1. *Extract the path derivation into a shared leaf* imported by name, so the two
   copies become one. There is no case for a hard dependency between the broker
   and the watcher, so the shared piece has to be a leaf that both can import
   without dragging in the transport.
2. *Teach the selector to both derivations*, and surface the resolved bus
   identity in the liveness probe and the status verb, per the acceptance
   criterion above.
3. *Move the whole fleet onto named buses at bring-up*, and let the unnamed bus
   become the untagged legacy path. This inverts what this document previously
   recommended, which was to move the unrelated projects first and leave the
   constellation where it was on the grounds that it had nothing to migrate.

   The reason for the inversion is a fact about timing, not a change of taste.
   The fleet is down and its log is drained: the constellation's 173 cursors
   have nothing pending behind them, so starting fresh on named roots loses
   nothing whatever today. Once the agents are up and carrying unread messages,
   the same move costs undelivered mail, and it costs it silently, because a
   cursor left on the old root cannot say what it was still owed. There is one
   window in which this migration is free, and it is open now.

   Cursors therefore start clean on the new roots and nothing is copied across.
   That is safe only under the same precondition, a drained log and a fleet that
   is down. If the fleet is already up when this is read, work the cost out
   again rather than inheriting this answer.

Steps 1 and 2 change no behaviour for anyone who does not set a selector, so
nothing multiplies until somebody names a bus.

* How the sequencing was settled

The earlier plan put the log lifecycle work first, on the reasoning that
segmentation multiplies logs and cursor directories, so it is better to multiply
machinery that already rotates and reaps correctly than machinery that does not.

That reasoning never applied to steps 1 and 2, which multiply nothing. Two
things then overtook it for step 3. The reaper turned out not to be broken. And
a clean departure, which this work had to build in any case, hands a departed
agent's cursor to its bus's broker and keeps it at the head of the log, which
removes the pathology the lifecycle work was most needed for. Segmentation
repairs part of the lifecycle rather than only multiplying it.

The deciding argument was the window. The migration is free exactly while the
fleet is down and the log is drained, and it stops being free the moment the
agents come back up. Sequencing behind the lifecycle work would have spent that
window to buy an ordering that was no longer needed.
