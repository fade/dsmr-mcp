#+title: The repository doctor: adopting a project into the harness
#+startup: showall

This describes =project-doctor=, the verb that adopts an existing repository into the harness,
and the lint gate that it and the scaffold install. The rules it follows in a repository we do
not own are in /The rules adoption follows/.

* Scope

Adopting a project means putting *our own apparatus* in place inside a repository,
so that our tooling can work there. It does *not* mean changing the project.

Getting that distinction wrong is the only way this can do real harm. The repositories in
question are usually dependencies of something we are building. They have their own history,
their own conventions, an upstream we do not control, and a maintainer who never agreed to our
habits. Anything of ours that becomes visible in their work product, their tracked tree, their
git log, anything a maintainer reads, is a defect.

So the feature has two halves that must not be confused:

- *Our apparatus*, which we install and which are invisible to the project:
  =.mallet.lisp= (the mallet linter's config), =scripts/lint-lisp.sh=, the lint gate, the
  entries in =.git/info/exclude=, and =.gate-baseline.md= holding the baseline of
  pre-existing lint findings. In a repository we do not own, every one of these is present on
  disk and excluded from version control. The gate lives inside =.git/= and so is invisible by
  construction.
- *The project's own layout*, which is theirs: the system definition, the source tree, the test
  tree, and the licence. We read it. We do not write it.

** The surface

One verb, =project-doctor=. It takes a repository path, an optional disposition answer, an
optional upstream URL, and an optional policy. *With no policy it assesses and writes nothing*,
and =dry_run= reports the same shape without writing. Repairing a difference, recording it as
debt, or accepting it as deliberate each require the caller to say so.

** Why a new verb rather than the existing scaffold

The scaffold creates a project from nothing. It takes an =overwrite= argument, and that path
deletes the target directory tree before writing. So the tool that looks like it could bring an
under-provisioned repository up to standard is in fact the destructive one, and =overwrite= is
exactly the argument somebody reaches for when a repository looks incomplete.

Adoption is the opposite operation. It acts on a repository that is not empty, that has history,
and that we must leave intact.

** The observation that prompted it

Of ten application repositories of ours, seven carry the linter config, the lint
script, and the pre-commit hook, and three do not. The config and the script co-occur exactly:
no repository has one without the other. The gate was arriving with the scaffold, or not at all.

* The design

** The disposition comes first, and I declare it

Nothing else can be decided until we know what a repository is to us. Guessing "ours" is the
dangerous answer: it is what would let our tooling become tracked content in somebody else's
project. So I declare it once, when a project is first tooled, as one of three dispositions:

- *ours*: code that originates with me.
- *contributing*: a third-party project I only contribute to.
- *forked*: somebody else's project that I forked, to shorten the acceptance chain or because
  its upstream is unmaintained. =zebra= and =boomer= are forked; our =parachute=, kept so that
  patches can go back upstream, is contributing.

A fork is one I take ownership of, so it matches a project of ours in every respect but one: it
keeps the licence it came with, and no licence text is ever written into it. Our agent and lint
files are tracked there as they are in my own projects, and the gate refuses a commit the same
way.

Remotes cannot decide it. Adoption forks the upstream under my own account and clones the fork,
so =origin= points at my account for third-party code exactly as it does for my own. Even before
that, the remotes left the question open for most of our own origins: across 251 repositories in
=$LISP_WORKSPACE=, 68 of the 90 with an origin of ours had no upstream and could have been either.
Licence files and author marks are no more reliable. Remotes now produce warnings and
nothing else: you are told when a project declared ours has an =upstream= remote, or when one
declared contributing has none, and the disposition stands either way.

*** Where the declaration lives

The declaration is one line in the project's =.envrc=:

#+begin_src sh
export DSMR_PROJECT_DISPOSITION=contributing
#+end_src

I keep it there so that it is answered once, when the project is tooled, and never becomes a
recurring question. =.envrc= goes into =.git/info/exclude= before the line is written, so the
file never reaches the tracked tree, and the doctor records nothing into an =.envrc= that is
already tracked. Every other line of the file stays as it was.

When a repository has no declaration, =project-doctor= returns the question, with the three
answers and what each means, and writes nothing. You answer by calling it again with
=disposition=. An assessment or a dry run uses your answer for that run only; a run with a policy
records it, and every later run reads it from the file and asks nothing.

The doctor reads =.envrc= as text and never sources it, and it never takes the value from the
server's own environment, which belongs to whatever directory the server was started in. The
value must be one of the three names, optionally quoted. Anything else, a shell expansion
included, is refused as unreadable, and so are two declarations that disagree.

Only the single-assignment form is read: =NAME=value=, optionally after =export= and blanks. A
line that assigns several variables, or uses =declare -x=, declares nothing, and you are asked.

The disposition is one per repository, because the gate and the findings record are shared by
all its worktrees. The main worktree's =.envrc= holds it, and every worktree reads it from there.
A recording made from a linked worktree is written into the main worktree's =.envrc=, and only
when that file lies inside the session root; otherwise you are refused with the file named, and
you record it from the main worktree. A linked worktree's own declaration still counts: when any
two worktrees' declarations differ, you are refused with both files named. A refusal of this kind
arrives before the doctor writes anything, so a refused run has changed nothing.

Recording keeps the =.envrc='s permission bits and, where the server may set it, its owner, so a
=0600= file holding a token stays =0600=. A file in any encoding is read and written back byte for
byte.

The doctor never rewrites a declaration, and an answer that differs from the recorded one is
refused. To change the disposition, edit the line and run a repair: the gate is rendered again
for the new value.

** One definition of shape, read by both the scaffold and the verb

The scaffold used to hold its file set privately, as a list of paths paired with rendered
content. That answers "write me a new project" and cannot answer "is this project the right
shape", because rendered content cannot express that a build script is optional or that a test
must assert on a result object rather than on a printed line.

Both now read a single catalogue. Each entry carries what it is, where it installs, whether the
scaffold emits it, and which group it belongs to. Two lists that agree today drift tomorrow,
and the drift is invisible until somebody compares them by hand.

** Differences are conditions, and recoveries are named

A difference between a repository and the shape is signalled as a typed condition, not returned
as a list of filenames. A string cannot be dispatched on, and neither can a path.

Three recoveries are named: repair it, record it as debt with the
diagnosis, or accept it as deliberately different. The distinction between something missing and
something deliberately different is the difference between a useful report and one that gets
ignored.

*** The limit that shaped the interface

A restart cannot cross a process boundary. Restarts established while handling one request are
gone by the time the caller sees the response, so they cannot be offered to a client the way
they are offered in-image.

The two layers are therefore split. Inside a single call, conditions and restarts work normally.
Across the wire, the verb takes a policy argument and returns a report; the restart names survive
as the vocabulary of that argument and that report, and the machinery does not.

** Risk is a severity, not a score

Installing a gate into a repository that already has lint findings must not dump those findings
as failures. The existing practice already answers this: a rule that blocks before the codebase
can satisfy it simply gets switched off, so an in-progress rule runs at an informational severity
and promotion is a separate, deliberate act.

There is no risk score, and not for want of trying to build one. Across our application
repositories, no ordering of development tempo and author count reproduces the one calibration on
record: a busier, older, ungated repository comes out *less* urgent than a quieter gated one. A
number built from those signals would have contradicted the only judgement available, and would
have been believed precisely because it was a number.

So there is a starting severity, in one place, and a baseline of what was already there.

** Ordering is the safety property

The entries in =.git/info/exclude= are written *before* anything else is written. If that order
is reversed, there is an interval in which our files exist in a repository that does not yet
ignore them.

This is enforced by the ordering of the code and by a check that replaces the write step with one
that fails, then asserts the exclude entries changed anyway. The broader never-leak check, which
asserts that nothing of ours appears in the repository's status, *cannot* detect a reversal: it
reads the repository after the operation finishes, by which time the exclude is correct either
way. Only the ordering check can see the interval.

* The rules adoption follows

** A project we contribute to is assessed only against our apparatus

Beyond installing the git-invisible components of our own apparatus, the doctor does not alter
the structure of a project declared contributing in any way. A flat library with its sources at the top level
and a =test/= directory is not missing anything we would supply.

The rule is encoded on whether a catalogue entry is apparatus, not on which tier it sits in,
because apparatus spans two tiers: a tier-based rule would silently drop =AGENTS.md=, =CLAUDE.md=,
the REPL-development guide, and =.envrc=, and would let a future non-apparatus entry added to the
gate tier start leaking.

I settled this after an earlier version wrote =src/main.lisp= and =tests/main-test.lisp= into
=cl-ppcre=, leaving two untracked entries of ours in a third party's status, carrying an AGPL
header into a BSD-2-clause project. The suite could not see it: every fixture committed those two
files before the run, so the never-leak check had only ever watched excluded apparatus being
written. The fixtures now include a flat library with no =src/= and no =tests/=, and the assertion
that a repair writes nothing but apparatus fails against the old behaviour.

** Adoption leaves the licence alone

Adopting a project is agreeing to contribute to it on its own terms, so I made adoption write no
licence file, no licence header, and no licence text into a project declared contributing or
forked, and change none that is there. A forked project keeps the licence it came with. The lint
script and the gate installed in such a repository carry no licence line at all. You can run the
doctor over a third party's tree and every licence byte in it stays where it was.

A project the scaffold creates is ours: when the scaffold initialises the repository itself, it
records the disposition ours, and its lint script names the licence you chose for it.

When I adopt a project that already has a repository checked out, the scaffold asks first. With
no disposition recorded in that repository, =project-scaffold= returns the same question the
doctor does, with the three answers and what each means, and writes nothing. Call it again with
=disposition= and the answer goes into that repository's =.envrc= before the project is written.
A repository the scaffold creates takes only ours, and with =init_git= false outside every
repository there is nowhere to record a disposition, so none is recorded.

The answer then governs what the scaffold writes there. In a repository declared contributing or
forked, the project carries no licence text at all, whatever =license= says: no =LICENSE=, and no
SPDX line, =:license= entry, or License section in any file. The result says so. The apparatus
paths the disposition keeps out of the index (for contributing, =CLAUDE.md=, =AGENTS.md=,
=prompts/repl-driven-development.md=, =.mallet.lisp=, =scripts/lint-lisp.sh=, and =.envrc=; for
forked, only =.envrc=, as in a project of ours) go into that repository's
=.git/info/exclude=, anchored under the new project, before any of its files is written. If the
scaffold fails after it recorded the disposition or changed the exclude, the error names those
writes, so you know the repository changed.

** The lint gate reports in a project we contribute to and refuses in our own

The gate lints the top-level forms a commit touches, and nothing else. Findings in forms and files
the commit leaves alone are not reported.

- *In a project declared contributing* the gate reports the findings inside the touched forms
  and never refuses the commit. Third-party code carries findings we did not write (=cl-ppcre=
  arrives with 93 findings across its 23 sources), and a gate that refused over those would
  refuse the first patch we offer upstream. What I want there is to know about defects near our
  own edits, and you see those in the commit's output while the commit proceeds.
- *In a project declared ours or forked* the same gate refuses a commit when a form it touches
  carries a warning or an error, or when the linter is missing or cannot lint a staged file. A
  finding that was already there in a form you did not touch never blocks you.

The mode is fixed when the doctor or the scaffold renders the gate. The gate reads neither
=.envrc= nor the environment to find it, so it behaves the same whether or not direnv is loaded.
A gate rendered for one mode reads as stale once the declaration changes to or from contributing,
and a repair renders it again.

** Every finding the gate shows is recorded

A break in function is always in scope for repair. Style is not, in a project I only contribute
to, but I still want every lint result I have seen tracked. So the gate appends each finding it
shows to =lisp-gate/findings.tsv= under the git common directory: one row per finding per
run, never deduplicated, shared by every worktree, and never tracked. Each row carries the time,
the gate's mode, the worktree and branch the commit was made in, the class, mallet's category,
the severity, the rule, the path, the line and column, and the message. A closing line after the
findings gives the record's path and the count in each class.

Commits in several worktrees at once append under a lock, =flock(1)= where it is installed and a
lock directory beside the record otherwise, so the header is written once and rows never
interleave. The category is read from mallet's JSON whatever order its keys arrive in. A record
that cannot be written or locked within about ten seconds costs you one notice line, never the
commit.

The class comes from the category mallet assigns each rule:

| mallet category                                        | class        |
|--------------------------------------------------------+--------------|
| correctness, suspicious, practice                      | functional   |
| cleanliness, style, format, metrics                    | style        |
| anything else, or a category that could not be read    | unclassified |

Severity cannot make this split. Over =cl-ppcre= mallet reports trailing whitespace and unused
variables as warnings, and a lambda list mixing =&optional= with =&key= as an error. Over our
own sources with every rule enabled, its suspicious and practice findings are warnings too. A
split by severity would put trailing whitespace beside real defects. Practice counts as
functional even though mallet describes such code as working. The table is one line at the top of
the gate.

Recording never changes whether a commit proceeds. A finding is recorded the same way whether it
refuses the commit or not, and when the record cannot be written you get one line saying so and
the same exit status you would have had.

A new project of ours is created with the gate in place: the scaffold writes the linter config,
the lint script, and the gate, and wires the gate when it creates the repository.

When the git init template seeds a pre-commit hook, every clone arrives with one, and that hook
belongs to whoever installed it. So I wired the gate through git's configured hooks,
which run it beside the existing hook, rather than replacing the hook file. Where git cannot run
configured hooks, the doctor and the scaffold install no gate and report it unresolved. Removing the wiring takes one =git config --unset= per entry.

* Modules

Twelve modules, a shell template for the gate, and a request surface, each with one
responsibility, layered so that each depends only on those above it and on modules that predate
this work.

| module                           | responsibility                                                        |
|----------------------------------+-----------------------------------------------------------------------|
| =src/git.lisp=                   | typed subprocess access to git; failures signal rather than returning nil |
| =src/template-render.lisp=       | template substitution, split out to keep the catalogue and the scaffold from depending on each other |
| =src/repo-classify.lisp=         | the declared disposition: reading it from =.envrc=, recording it, and warning where the remotes disagree |
| =src/project-shape.lisp=         | what a shape entry is, and what may be said about it                   |
| =src/project-shape-catalog.lisp= | the entries themselves, and which are assessed for which kind of repository |
| =src/project-exclude.lisp=       | reading the exclude template, merging, and repairing with a backup      |
| =src/project-deviation.lisp=     | the condition types and the three named recoveries                   |
| =src/project-gate-scan.lisp=     | running mallet over existing sources to discover pre-existing findings |
| =src/project-debt.lisp=          | the severity, and rendering the baseline                               |
| =src/project-hook.lisp=          | wiring the gate into git's configured hooks                            |
| =src/project-assess.lisp=        | read-only: what differs, writing nothing                               |
| =src/project-doctor.lisp=        | the engine that applies a policy and reports what it did               |
| =templates/lisp-gate.sh=         | the gate itself, rendered informational or blocking, and its findings record |
| =src/tools/project-doctor.lisp=  | the request surface                                                  |

The scaffold was changed to read the catalogue rather than hold its own copy, to make a new project
a git repository from the start, and to install the gate. The second change matters more than it
looks: the global git init template already seeds the correct exclude entries into every newly
created repository, so once the scaffold runs =git init=, the existing provisioning does the
writing. No exclude list is reimplemented in Lisp.

** Structural choices

The distinction between a repository we own and one we do not is carried in the *type* of a
shape entry rather than checked at each site that writes.

The baseline of pre-existing findings distinguishes *absent* from *empty*. If mallet cannot
be run, the result is "not enumerated" and nothing is written. A baseline asserting zero findings
and one nobody populated look identical once written, and the written one would be believed.

* Verification

Every check was proven able to fail before its success was accepted. Deliberate breaks were
seeded against each property and watched to go red, then reverted, with the restoring run checked
for recompilation so that a stale compiled file could not supply a false green.

Assertions that look equivalent frequently are not. Eight of the seeded breaks reddened one
assertion while a sibling that appeared to test the same thing stayed green, and one break
reddened nothing at all, because the property is enforced in two places. Two of the checks in
this suite would be deleted as redundant by anyone who ran a break and read only the pass and
fail totals.

Fixtures are real git repositories rather than plain directories, because =.git/info/exclude= and
the hooks directory do not exist otherwise. The gate's tests drive the real linter and the real git, and
its parsers follow output recorded from both.

** Driven against a real third-party repository

A green suite once passed while the doctor wrote into a third party's tree, so I drove the shipped
verb against a fresh clone of =cl-ppcre= as well: an assessment, a dry run, recording as debt, a
repair, and a second repair. Every result was read from the clone with git and the filesystem,
never from the doctor's own report, by these checks:

- =git status --porcelain= is empty;
- the tracked file list is unchanged;
- HEAD is unmoved;
- every tracked file is byte-identical;
- nothing new on disk carries licence text, and no new file is named like a licence;
- the pre-commit hook the clone arrived with is byte-identical;
- git lists the gate as an enabled pre-commit hook.

Each check was first shown failing in the same clone on a planted violation: an untracked file, a
staged extra path, an extra commit, a byte appended to =LICENSE=, a licence identifier in a new
file, a byte appended to the hook, and the gate disabled in config. Each passed again once the
plant was removed.

After every step the checks passed. The baseline recorded 93 sites, the count an independent
linter run gives over the same 23 sources. A second repair changed nothing on disk or in the hooks
directory and wrote no second exclude backup. With an edit staged inside a form of =api.lisp= that
already holds a finding, the gate reported that one finding, out of the ten in the file, and the
commit proceeded; a planted =ignore-errors= in the same form appeared beside it, and the commit
still proceeded.

A project created through the scaffold records the disposition ours and carries the linter
config, the lint script, and a wired, blocking gate; its generated files pass that gate, and a
planted =ignore-errors= is refused.

The findings record was checked against mallet's own output, recorded for a file planted with one
finding each in the correctness, format, and style categories: the rows match it field for field,
in both modes, across two runs and from a linked worktree. With the JSON run made to fail, every
row is unclassified and the gate's output and exit status are unchanged.

Both cold suites, =make test= and =make test-integration=, pass on every test this feature adds or
changes. The two are separate commands because =make test= does not walk =tests/integration/=.

* Outstanding verification

The checks that need a running server on a rebuilt image have not been done, because that needs
a rebuilt image and a reconnect.

Separately, whether a client rejects a prompt carrying a required field is still untested.
Nothing in this design depends on the answer, because the disposition question crosses the
wire as an ordinary result answered by an ordinary follow-up call, but it is unverified.

* Size

Twelve modules and several thousand lines is a lot for "put our apparatus into a
dependency", and most of the volume is in three places.

Roughly half is tests and fixtures, and that is where the value showed up: every defect the suite
found was found by a check that had been proven able to fail. The one defect the suite missed was
the layout write described above, which no check was positioned to see.

The disposition module reads and records a declaration instead of inferring one. I tried
inference first, and the ambiguous case turned out to be the common one. That was not knowable in
advance.

The part that could reasonably be smaller is the separation between assessment, deviation types,
debt recording, and the engine. Those are four modules that could have been two. They were kept
apart so that the read-only path provably writes nothing, which is worth something, but it is a
judgement call and a reasonable person could collapse them.

The finding worth carrying is the one about the layout. For a while this feature wrote into a
third party's tree, which is the one outcome the whole design exists to prevent, and thousands of
green assertions never saw it. The tests could not have found it, because the fixtures were built
to satisfy the expectation being tested. Driving the real verb against a real repository could,
and did.
