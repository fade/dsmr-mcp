#+TITLE: dsmr-mcp — Operations & Runbook

This is the field runbook for =dsmr-mcp=. When the server misbehaves,
find the matching failure mode below and follow the
symptom → cause → check → fix recipe. It documents the health surface
(=backend-status= in either mode, =pool-status= for the hermetic pool)
and the four failure modes that actually happen in the field: cold
start, attached-mode degradation, the hermetic-worker crash loop, and
alive-lsp absence.

#+begin_quote
*Security note.* None of these recipes ever tell you to relax a control
to make a symptom go away. Questions about binding off-loopback or
exposing the server to the network belong in [[file:threat-model.org]],
not here — =dsmr-mcp= is a trusted, localhost-only tool.
#+end_quote

See also: [[file:index.org]] · [[file:configuration.org]] (full env-var
matrix) · [[file:modes-and-transports.org]] · [[file:threat-model.org]].

* Cold start

=dsmr-mcp= boots through =dsmr-mcp:run=, which resolves every setting
with the precedence *keyword argument > =DSMR_*= environment variable >
=.dsmr-mcp.conf= > built-in default*, then dispatches to the selected
transport.

** Boot by transport

- *stdio* (the default) — =(dsmr-mcp:run)= or
  =(dsmr-mcp:run :transport :stdio)=. Blocks reading =*standard-input*=
  until EOF. This is the transport an MCP client launches as a
  subprocess, and speaks one JSON-RPC message per line.
- *TCP* — =(dsmr-mcp:run :transport :tcp :port 7000)=. A threaded,
  multi-client line-delimited JSON-RPC listener, one session per
  connection.
- *HTTP* — =(dsmr-mcp:run :transport :http :port 7000)=. Streamable HTTP
  over Hunchentoot for Claude Code URL mode.

See [[file:modes-and-transports.org]] for the full transport and mode
detail.

** Environment surfaces that select mode and Slynk target

| Variable             | Effect                                                                                                                                                              |
|----------------------+-------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| =DSMR_TRANSPORT=     | =stdio= (default), =tcp=, or =http=.                                                                                                                               |
| =DSMR_MODE=          | =attached= (default), =hermetic=, or =auto=. =auto= probes the Slynk listener and falls back to =hermetic= when it is unreachable; explicit =attached= never falls back. |
| =DSMR_SLYNK_ATTACH=  | =host:port= of the Slynk listener for attached mode (e.g. =127.0.0.1:4005=).                                                                                       |
| =DSMR_BIND=          | Listener bind address for =tcp= / =http=. Default =127.0.0.1=.                                                                                                     |
| =DSMR_ALLOW_REMOTE=  | Must be =1=, =true=, or =yes= to allow a non-loopback =DSMR_BIND=. Without it, a non-loopback bind is refused at startup (see [[*It will not start — first things to check][It will not start]]). |
| =DSMR_LOG_LEVEL=     | =debug=, =info= (default), =warn=, or =error=. Logs are structured JSON on *stderr*, never stdout.                                                                 |
| =DSMR_PROJECT_ROOT=  | Server working root; defaults to the process cwd.                                                                                                                  |

A malformed value for =DSMR_TRANSPORT=, =DSMR_MODE=, =DSMR_LOG_LEVEL=, or
=DSMR_PORT= signals a typed =invalid-config-value= at startup with a
human-readable message naming the offending variable — so an env-var typo
fails loudly and early rather than booting into a surprising mode. The
exhaustive variable reference lives in [[file:configuration.org]].

** Confirm a clean load on a cold FASL cache

Before launching the server, confirm the system compiles and loads
cleanly from a cold cache. In a fresh SBCL:

#+begin_src lisp
(asdf:load-system :dsmr-mcp)
#+end_src

A clean cold load returns with no aborting warnings. To force a truly
cold compile, clear the ASDF output cache first (typically
=~/.cache/common-lisp/=) so stale FASLs cannot mask a build break.

** It will not start — first things to check

1. *Package-inferred cold-build dependency errors.* =dsmr-mcp= is a
   =package-inferred-system=: each file's =defpackage= declares its own
   external dependencies. A warm REPL can hide a missing declaration
   because the package already exists in the image; a cold load surfaces
   it as =Package X does not exist=. If =(asdf:load-system :dsmr-mcp)=
   fails this way on a cold cache, the offending file's =defpackage= is
   missing an =:import-from= for the package it uses. Always confirm the
   cold load, not just the warm one.
2. *Quicklisp / userinit noise on the stdio channel.* On the stdio
   transport, anything written to stdout that is not a JSON-RPC message
   corrupts the channel and the client sees a protocol error. Once the
   server is serving, this cannot happen — it claims the stdio streams for
   the wire and walls the global standard streams off from every thread —
   so the remaining hazard is *startup* chatter printed before that claim:
   a =~/.sbclrc= or Quicklisp banner that writes to stdout while the
   system loads is the usual culprit. Logs are deliberately routed to
   stderr for this reason; keep startup chatter off stdout (redirect the
   load phase to stderr in your launch wrapper if your init files print).
3. *Non-loopback bind refused.* If =tcp= / =http= startup signals
   =invalid-config-value= for =DSMR_BIND=, the bind address is not
   loopback and =DSMR_ALLOW_REMOTE= is not set. This is the safety gate
   working as designed — see [[file:threat-model.org]] before changing
   it.
4. *Hermetic mode wedged at startup.* When =*mode*= resolves to
   =hermetic=, =run= initializes the worker pool, which pre-warms the
   worker system's FASL cache once in the parent before any child spawns.
   On a cold cache this adds a one-time compile to startup; on a warm
   cache it returns immediately.

* Health checks

** =backend-status=: ask this first, in either mode

=backend-status= reports the health of whichever backend this server is
using, so you do not have to know which one that is before you can ask.
It takes no arguments.

In hermetic mode it reports pool liveness, the most recent ping round
trip, circuit-breaker state with the seconds left in any cooldown, the
crash count inside the current window, how many worker incarnations have
been issued, and a per-worker breakdown of state, liveness, last ping and
missed pings. In attached mode it reports this session's liveness
classification, last probe round trip, connection epoch, and whether a
connection is open; the breaker and crash-history fields come back marked
not applicable rather than zero, because a zero would read as a clean
measurement where nothing was measured at all.

Every classification arrives with what it establishes, what it does not,
how it was obtained, and what would flip it, so no value has to be read
on trust. It answers about the backend only. For the state of a
coordination bus, call =bus-inspect= instead.

** =attach-reset=: reopen this session's connection

=attach-reset= force-drops and reopens the calling session's connection
to the developer's Lisp image, in place, with no server restart. Reach
for it when the image accepts connections and answers nothing, or after a
fault has left the wire unusable. It resets the wire, not the image:
definitions and application state in the developer's image survive.

It touches only the calling session's own connection and takes no
arguments, so no other session can be named or dropped. The response
carries the connection epoch after the reset, which is what makes the
reset observable to a call that was already in flight. Available in
attached mode only.

** =pool-status= — hermetic-mode health verb

=pool-status= is the health surface for hermetic mode. It is an MCP verb
that takes no arguments and returns a structured JSON body with these
fields:

| Field                | Meaning                                                                                                                                      |
|----------------------+----------------------------------------------------------------------------------------------------------------------------------------------|
| =pool_running=       | =true= when the pool's health monitor is live.                                                                                              |
| =total_workers=      | Count of workers the pool holds: bound, standby and hibernated.                                                                             |
| =standby_count=      | Warm workers ready for immediate assignment. Zero unless =DSMR_WORKER_POOL_WARMUP= asks for some.                                           |
| =bound_count=        | Workers bound to a session and running; hibernated ones are counted in =hibernated_count= instead.                                          |
| =hibernated_count=   | Workers whose world is saved to disk and whose process has ended.                                                                           |
| =max_hibernated_workers= | The most workers this server keeps hibernated (=DSMR_MAX_HIBERNATED_WORKERS=, default 8).                                                  |
| =resident_count=     | Workers with a running process.                                                                                                             |
| =max_pool_size=      | Configured ceiling (=DSMR_MAX_POOL_SIZE=, default 16). Resident workers count against it; hibernated ones do not.                           |
| =warmup_target=      | Configured standby target (=DSMR_WORKER_POOL_WARMUP=, default 0).                                                                           |
| =pressure_relief=    | =active= when the pool is answering a live host bus service, else =inactive=.                                                              |
| =worker_core=        | The worker core new workers boot from, or =null=.                                                                                           |
| =worker_core_status= | =in use=, =unset=, =missing=, or =disabled:= and the reason (a core that would not boot is set aside for the life of the server).          |
| =workers=            | Per-worker array, described below. The Slynk port is deliberately omitted so the health view cannot be used to bypass MCP policy.          |

Each entry in =workers= carries =id=, a truncated =session=, =tcp_port=,
=pid=, =state= and the liveness fields =backend-status= also reports, plus:

| Field               | Meaning                                                                                                   |
|---------------------+-----------------------------------------------------------------------------------------------------------|
| =state=             | =standby=, =bound=, =hibernating= (saving its world), =hibernated=, =resuming=, =crashed=, =released= or =dead=. |
| =stateful=          | It has run a call that can leave state behind, so it is hibernated rather than stopped under pressure.    |
| =busy=              | A call is holding it now. A busy worker is never stopped or hibernated.                                  |
| =boot=              | How its process started: =core=, =source= or =resumed=.                                                   |
| =last_activity=     | Unix seconds of its last call.                                                                            |
| =core_bytes=        | Size of its last saved core.                                                                              |
| =core_age_seconds=  | How long it has been hibernated.                                                                          |
| =last_hibernate_ms= | How long its last save took.                                                                              |
| =last_resume_ms=    | How long its last resume took.                                                                            |
| =refused_reason=    | Why it was last refused: for hibernation busy, threads of its own, =at-limit=, too little disk, a refused path, a failed or slow save; for a stop =no-core= (it loaded from source, so its replacement would too). |

=pool-status= is only meaningful in hermetic mode. Called when =*mode*=
is *not* =:hermetic=, it returns an informative =isError= ("pool-status
is only available in hermetic mode") rather than empty or misleading
data — so seeing that error is itself a signal that the server is running
attached, not hermetic.

** Attached-mode health

=backend-status= is the attached-mode health surface: call it for the
session's liveness classification, its last probe round trip, and its
connection epoch. A trivial =repl-eval= round trip (evaluate a constant,
confirm the value comes back) still works as a coarse confirmation, but
when the image has stopped answering the round trip just hangs with it.
=backend-status= separates an image that accepts the connection and no
longer answers from one that is not listening at all: a different fault
and a different repair. It classifies =healthy=, =wedged= or =dead=.
⚠ It does not separate a wedged image from a merely slow one. The probe
asks a trivial question under a short budget, so an image that answers
that question quickly and then takes thirty seconds over real work
reports =healthy=.

#+begin_example
repl-eval  code: "42"
#+end_example

A successful response (the value =42=, no =isError=) confirms the Slynk
connection to the attached image is live end-to-end. A structured
=isError= with a =NETWORK_ERROR=-class message means the listener is
unreachable or the connection dropped — see
[[*Attached-mode degradation][Attached-mode degradation]] below. Because
the connection is opened eagerly at session initialize and reopened
lazily on the next call after a drop, this probe doubles as a reconnect
trigger.

* Attached-mode degradation

The Slynk listener =dsmr-mcp= attaches to is gone, or the connection
dropped mid-call.

- *Symptom.* =repl-eval= and the =inspect-*= verbs return a structured
  =isError= whose message names a Slynk connection error (=NETWORK_ERROR=
  class — "attach: Slynk connection error: ..."). Output and inspection
  verbs stop working; the rest of the protocol (=tools/list=, filesystem
  verbs) keeps responding.
- *Cause.* The attached image's Slynk listener is unreachable — the host
  image was stopped or restarted, the listener was never started on the
  configured =host:port=, or the TCP connection was severed mid-eval.
- *Behaviour (fail-closed, reconnect on next call).* Network errors fail
  closed: the dispatcher catches the connection error, *discards the
  cached connection*, and returns the structured =isError= — it does
  *not* retry inside the same call, and it does *not* silently fall back
  to a hermetic worker. The next call reopens the connection lazily on
  demand. When a call reopens a previously-dropped connection, its
  =stdout= is prefixed with a reconnect note warning that in-image state
  may have reset (definitions, packages, and registered object IDs from
  before the drop are gone).
- *Check.* Call =backend-status= first: it classifies this session's
  connection and says what that classification does not establish. Then
  confirm the Slynk listener is actually up on the configured
  address. The target is whatever =DSMR_SLYNK_ATTACH= (or the
  =:slynk-attach= keyword) points at — e.g. =127.0.0.1:4005=. A plain TCP
  probe to that =host:port= tells you whether the listener is accepting
  connections.
- *Fix.* Bring the listener back up on the configured =host:port= (start
  Slynk in the host image again), then *re-issue the call*: the
  dispatcher reconnects on the next request and the connection cache
  self-heals, with no server restart. If the listener is up and calls
  still hang, =attach-reset= drops and reopens the connection in place.
  Expect the one-time reconnect note on the first successful call after
  recovery.

* Hermetic-worker crash loop

A session's hermetic worker keeps crashing, and calls for that session
start failing fast.

- *Symptom.* Tool calls for the affected session begin returning an error
  immediately (fail-fast), with a message naming the *circuit breaker*
  and a remaining cooldown. Earlier you may have seen a single
  crash/reset notification followed by a normal call, then repeated
  crashes.
- *Cause.* The circuit breaker tripped. Each session gets exactly one
  crash-reset notification per crash and the next call after a crash
  normally succeeds against a fresh replacement worker — but if a worker
  crashes *3 times within a 5-minute (300-second) window*, the breaker
  trips for that session. While tripped, =get-or-assign-worker= fails
  fast for a *60-second cooldown* instead of spawning yet another
  replacement, so a genuinely broken workload (an eval that reliably
  kills the worker) cannot burn the machine down in a tight respawn loop.
- *Check.* Call =backend-status= for the breaker state and the seconds
  left in its cooldown; its =pool.liveness=, =pool.bound_count= and
  per-worker =state= entries say whether the session still has a live
  worker or the breaker has removed it. =pool-status= (hermetic mode
  only) reports the same pool at the top level instead, as
  =pool_running= and =bound_count=. A
  repeatedly-shrinking =total_workers= for the session, paired with the
  fail-fast error, confirms the crash loop.
- *Fix.*
  - *Wait out the window.* The breaker self-clears after the 60-second
    cooldown; the next call for the session then spawns a fresh worker
    normally. If the underlying workload is transient, this is the whole
    fix.
  - *Reset manually.* Ending and re-establishing the session
    (=release-session=) clears the breaker state immediately, so a
    restarted session is not held back by a prior trip.
  - *Clear a wedged worker.* If a worker is hung rather than crashing,
    =pool-kill-worker= kills the bound worker without ending the session;
    the next call spawns a fresh one. (Its reset variant also clears the
    breaker for the session.)
  - *Address the root cause.* A breaker that keeps tripping means the
    workload itself reliably kills the worker — fix the offending code or
    input rather than repeatedly resetting the breaker.

The circuit breaker is a denial-of-service mitigation (3 crashes / 300 s
window, 60 s cooldown); see the corresponding STRIDE row in
[[file:threat-model.org]].

* Memory pressure and hibernated workers

Where the host bus service runs, it watches the host's memory and, under
pressure, asks pools to stop fresh idle workers and hibernate stateful idle
ones (see [[file:architecture.org::*Worker lifecycle][Worker lifecycle]] for why
and in what order). A pool acts only on those requests. With no host service,
nothing is ever stopped or hibernated, and a worker lives until its session
ends. =pool-status= reports =pressure_relief= as =active= when its pool is
answering a live service.

** Where hibernated cores live, and who removes them

Each MCP server keeps its workers' saved worlds at
=~/.local/state/dsmr-mcp/hibernate/<server pid>-<start time>/<worker id>.core=
(under =$XDG_STATE_HOME= when that is set). The directories are readable by
you alone (0700) and so are the files (0600), because a core holds everything
the worker held. They sit on disk rather than tmpfs, outside any repository,
and must never be synced between hosts.

A core is removed when its worker resumes, when its session is released, when
the worker is killed, and when the server shuts down. A server that dies
without shutting down leaves its directory behind: the next pool to start on
the host sweeps every directory whose server is gone, and the host service
does the same once a minute. A server is named by its pid and its start time
together, so a pid the kernel has since handed to another process never makes
a dead server's cores look live.

A worker let go in the middle of a save, by a release, a kill or the server
shutting down, takes its saving child with it, and its partial core is
deleted at once. A shutdown never waits for a save to finish: it ends the
save, so restarting a server takes seconds however large the world being
saved, and the save in progress is all that is lost.

A resume that fails for a reason that may pass (the handshake ran out of time
on a slow disk, the kernel refused the fork for memory, the process was killed
while it loaded) gives up nothing: the worker stays hibernated with its core
in place, that call fails with an error saying the world is still saved, and
the session's next call tries again. The first such failure writes a
=worker-resume-deferred= warning to the fleet error log, so you see a world
that has stopped resuming before it is given up. A resume is retried from the
runtime that wrote the core, even after the =sbcl= package was upgraded under
a running server, because the server's own executable is still the old build.

Retries are bounded. A failure that looks as if it may pass can be permanent
(a core damaged inside the file makes the resumed process die the same way
every time), so once =DSMR_MAX_RESUME_ATTEMPTS= resumes in a row (default 3)
have failed, the world is given up as described below: the core is kept under
=hibernate/failed/= and the session gets a fresh worker with a notice saying
its saved world could not be restored. A resume that succeeds starts the count
again. To give the world up sooner, kill the session's worker with
=pool-kill-worker=.

A core the runtime refuses outright, one whose runtime is gone, and one that
has reached the retry limit above are final. It is moved to =hibernate/failed/= and kept for diagnosis, and nothing
ever resumes from that directory. The newest failed core of every worker whose
server is still running is always kept, so a burst of failures across many
sessions never deletes one session's world to make room for another's; beyond
those, the two newest are kept and older ones are deleted. Read the
=worker-resume-failed= line in the fleet error log for the cause, then delete
the file when you are done with it.

The dead-owner sweep removes a server's files only on positive evidence that
it is gone: no process with its pid, or one that started at another time. When
=/proc= cannot be read (the reader is out of descriptors or memory) everything
is kept, and the service logs =owner-state-unknown=.

Hibernation is refused when free space on that filesystem is below twice the
worker's expected core size, so a save cannot fill the disk. The worker stays
resident and =pool-status= shows why in its =refused_reason=.

Each server also keeps at most =DSMR_MAX_HIBERNATED_WORKERS= workers (default
8) hibernated, saving or resuming at once; a worker being resumed still owns
its core, which stays on disk if the resume fails. Without a limit, a server
whose sessions come and go without being released would keep saving their
worlds until the disk check alone stopped it, with the disk nearly full. At the limit a request to
hibernate is refused with =at-limit=, the server's record tells the host
service it is full so the service asks it for no more saves, and the service
turns to other workers. The free-space check above still applies below the
limit.

** Capacity

A hibernated session does not count against =DSMR_MAX_POOL_SIZE=: it has no
process and holds no memory. It still needs a place to resume into. If the
pool is full when the session's next call arrives, that call fails with
=pool-capacity-exceeded= and the session stays hibernated with its world
intact on disk. Nothing hibernates another worker to make room. Retry once a
session ends or a worker is stopped, or raise =DSMR_MAX_POOL_SIZE=.

** A pool that stops answering

The service asks one pool at a time and nothing more while a request
stands, so it guards against a pool that has stopped listening while its
server still runs. A pool rewrites its worker record at least every five
seconds; a record older than thirty seconds is not acted on. A request left
unanswered for five minutes is withdrawn, and that pool is passed over for
the next five minutes while relief moves on to the other pools. When nothing
else is left, the episode is reported as =memory-pressure-unrelieved=, so
systemd-oomd is never left to choose silently.

** The memory line of =--host-status=

=~/.local/bin/dsmr-bus-watch --host-status= prints one more line after the
service line once the service watches memory:

#+begin_example
memory state=ok hibernated=0 resident=3 since=1760584000 some=0.0 available=61 last-action=-
#+end_example

=state= is =ok=, =pressure=, or =unknown= before the first reading.
=hibernated= and =resident= count the workers of live servers. =since= is
when the state last changed and =last-action= when a pool was last asked to
give memory back, both in Unix seconds (=-= for never). =some= is the
ten-second "some" stall figure and =available= the share of memory still
available, in whole percent. Pressure never changes the command's exit status:
it is information for a leader, not a fault of the service. A host whose
service predates memory relief prints no such line.

** Fleet error log codes

The service writes to the fleet error log, where a leader listens, only what
someone may have to act on. Each relief request is routine and goes to the
service's own log instead.

- =memory-pressure= (WARN): the host has entered pressure, with the readings
  that showed it, and relief has begun. A leader notes it in the footer;
  nothing needs doing unless one of the two lines below follows. When pressure
  ends, a =recovered= line for the same code closes the episode.
- =breaker-tripped= naming =memory-pressure= (ERROR): the service asked for
  relief 30 times within ten minutes and pressure kept coming back, so it has
  paused relief for a minute. Memory is being taken faster than idle workers
  can give it back. A leader carries it to the operator, who decides whether
  to park sessions or stop work on the host.
- =memory-pressure-unrelieved= (ERROR, once per episode): the host has been
  short of memory for over a minute and no idle worker is left to stop or
  hibernate, or none in a pool that is still answering; the line says how
  many pools were passed over. Nothing the service can do will help. A leader puts it in front
  of the operator at once; ending or parking sessions is the only relief left.
- =worker-resume-failed= (ERROR, written by the pool, =id= naming the session):
  a hibernated world could not be resumed, because the runtime refused the
  core or the runtime that wrote it is gone. A failure that may pass never
  writes this line. The session already received a fresh worker and a reset
  notice naming the cause, and the core is kept under =hibernate/failed/=. A leader tells whoever owns that session that its
  in-image state is gone, and reports it if it happens again.

Three WARN codes say the service set something aside: =memory-threshold-ignored=
(a setting it could not use, see [[file:configuration.org][Configuration]]),
=memory-request-stale= (a request no pool answered within five minutes, which
it withdrew, passing that pool over for the next five minutes) and =worker-record-mismatch= (a worker record whose name and
contents disagree, which it never acts on).

** The core images

=make core= builds two images: =dsmr.core= for the MCP server, then
=dsmr.core.worker= for hermetic workers, each verified before it replaces the
one installed, with the previous image kept beside it as =.prev=. Run
=make core-worker= to rebuild the worker image alone and
=make core-verify-worker= to check an installed one. The launcher judges the
worker image by the same freshness rule as =dsmr.core=, rebuilds it in the
background when it is stale, and passes it to the server only while it is
fresh, so a server started meanwhile simply loads its workers from source.
Running servers keep the image they started with until they restart.

To measure what idle workers cost on a host, run

#+begin_src sh
scripts/measure-worker-footprint.sh dsmr.core.worker 8
#+end_src

It starts that many workers from the image one after another, sums their
proportional set size, stops them all, and prints one line:
=workers=8 total_pss_kb=... avg_pss_kb=... max_handshake_ms=... median_handshake_ms=...=.
On the development box eight workers averaged about 39 MB each and reached
their handshake in about 80 ms.

* alive-lsp absence

The syntax-intelligence verbs degrade because no alive-lsp server is
available.

- *Symptom.* =lsp-completions=, =lsp-hover=, =lsp-diagnostics=, and
  =lsp-code-actions= return reduced or empty results compared to a
  fully-attached alive-lsp. They do not hard-fail — the server stays up
  and the rest of the verb surface is unaffected.
- *Cause.* =dsmr-mcp= resolves an LSP server per project root with an
  *attach-else-spawn* strategy: it first probes =127.0.0.1:8006= for an
  already-running alive-lsp, and on refusal spawns a child SBCL running
  alive-lsp. Both paths can be unavailable: no listener on 8006 *and*
  spawn disabled because =DSMR_ALIVE_LSP_DIR= is unset (spawn requires a
  configured alive-lsp source tree). When neither attach nor spawn
  succeeds, the LSP-backed verbs fall back to *in-process Eclector
  parsing* — enough for structural / paren-level answers, but without
  alive-lsp's full completion / hover / diagnostic intelligence.
- *Check.* Confirm whether an alive-lsp is reachable. Either something
  should be listening on =127.0.0.1:8006=, or =DSMR_ALIVE_LSP_DIR= should
  point at an alive-lsp checkout so the server can spawn its own. With
  neither, you are on the Eclector fallback.
- *Fix.* Point =dsmr-mcp= at a real alive-lsp:
  - *Spawn mode.* Set =DSMR_ALIVE_LSP_DIR= to the alive-lsp source
    checkout and restart the server. It will spawn a child alive-lsp on
    an OS-assigned port on first use and cache it per project root.
  - *Attach mode.* Start an alive-lsp listener on =127.0.0.1:8006= before
    launching =dsmr-mcp=; the server attaches to it instead of spawning.
    (=DSMR_LSP_STARTUP_TIMEOUT= bounds how long a spawn waits for the
    server's startup line, default 30 s.)

* Coordination bus

The [[file:coordination-bus.org][agent coordination bus]] is a single-host,
broker-mediated message log shared by every =dsmr-mcp= process on the machine. It
self-manages — the broker is elected lazily on first use and fails over
automatically — so it has few operational knobs, but a handful of recipes cover
the field cases.

- *Is it up, and what is waiting?* =bus-status= returns =broker_running= (whether
  any process holds the election lock) and =pending= (this agent's backlog). It
  consumes nothing. Both are readings taken at that instant; for the state of the
  bus itself, see the next item.
- *What state is the bus in?* =bus-inspect= answers the inventory question,
  read-only: which broker is serving the bus and against what source, whether a
  member leaving right now would seal the log, the log's head and generation and
  the sealed logs behind it, every recorded position with the stranded ones
  flagged, and which identities are enrolled and reading. Each value states what
  it establishes and what it does not, so no reading has to be taken on trust.
- *Backlog not draining.* =bus-receive= with the default non-blocking timeout
  delivers everything past your cursor and advances it. If =bus-status= shows a
  broker but =pending= stays at zero when you expect messages, confirm you are
  using the identity you published under — a different =DSMR_BUS_AGENT= or an
  =ephemeral= call reads a *different* cursor. See [[file:coordination-bus.org::*Agent identity][agent identity]].
- *Broker appears stuck.* Kill the broker process. The next participant
  contending for the election lock takes over and replays the log; no message is
  lost, because the write-ahead log is the authority and cursors are durable.
- *Reset a participant.* Delete its cursor file under
  =$XDG_STATE_HOME/dsmr-mcp/bus/cursors/= (or =~/.local/state/dsmr-mcp/bus/cursors/=)
  to re-receive from the start of the current log.
- *Read the bus files directly.* Everything lives under =$XDG_STATE_HOME/dsmr-mcp/bus/=:
  the active =bus.wal=, the =cursors/= directory, the broker's =broker.log=, and
  any rotated =bus.wal.archive-*= logs from clean shutdowns.
- *Single host only.* The bus is machine-local (=flock= election, =ipc://=
  sockets); there is no cross-host transport.
