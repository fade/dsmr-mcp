#+TITLE: dsmr-mcp — Agent Coordination Bus
#+SUBTITLE: How sibling agents and subagents coordinate on one host

The *coordination bus* lets multiple agents on the same machine pass messages to
one another — sibling agents driving different Lisp projects, and subagents
spawned inside one project. It is a single-host, broker-mediated, durable message
log: an agent publishes a line, every other participant receives it exactly once,
and a participant that restarts resumes exactly where it left off.

It exists for the multi-project workflow this server already encourages. If you
run one global MCP install across several Lisp projects (see
[[file:configuration.org::*direnv per-project setup][direnv per-project setup]]),
each project's agent is otherwise blind to the others. The bus is the back-channel
that lets a project leader announce progress, hand off work, or acknowledge a
sibling — without any shared database, network service, or manual wiring.

It is *localhost only* and shares the server's trust posture: it is a
coordination convenience among agents the operator already trusts, not a security
boundary. See the [[file:threat-model.org][threat model]].

* The three verbs

The bus surface is three tools. Their full input schemas live in the
[[file:tools.org][tool reference]]; this is the operational summary.

- =bus-publish= — broadcast a message. Fire-and-forget: the line is appended
  durably to the bus log and every other participant will receive it. Takes a
  required =message= string.
- =bus-receive= — receive messages this agent has not yet seen, advancing its
  cursor so each is delivered once. With no =timeout_ms= (the default) it returns
  immediately with whatever is pending (catch-up); set =timeout_ms= to block that
  long waiting for the first message.
- =bus-status= — report whether a broker is running and how many messages are
  waiting for this agent, *without* consuming them. Use it to peek.

All three accept two optional identity controls, =agent_id= and =ephemeral=,
described under [[*Agent identity]] below.

A minimal round trip: =bus-status= to see the broker is up and the backlog,
=bus-receive= to drain it (advancing the cursor), =bus-publish= to broadcast back.

* Agent identity

Every participant on the bus has an identity of the form =<namespace>/<name>=.
The *namespace* is the project root path, so two projects never collide even if
they pick the same name. The *name* is what distinguishes a long-lived agent
(=main=, =leader=) from a one-shot helper. A participant's durable message cursor
is keyed on the full identity, which is why a named agent resumes its place across
restarts and an anonymous one does not.

The session resolves its identity by a fixed four-rule order — the first rule
that applies wins:

1. *=ephemeral t= (explicit opt-out).* Forces a fresh, one-shot ephemeral
   identity for this call, ignoring rules 2 and 3. This is how a subagent that
   inherits the project environment avoids stealing the main agent's cursor.
2. *Explicit =agent_id=.* A non-empty =agent_id= argument names a stable
   participant under the project namespace; it resumes its own cursor across
   restarts.
3. *=DSMR_BUS_AGENT= environment variable.* A non-empty value names the project's
   stable main-agent identity. This is the normal case: the per-project =.envrc=
   exports it (defaulting to the project directory name), so the project's primary
   agent keeps one durable cursor across every launch. An empty value is treated
   as absent.
4. *Ephemeral default.* With none of the above, the session gets an auto-unique
   ephemeral identity for the duration of the session. It does not resume a prior
   cursor.

The practical upshot: give your project's main agent a stable =DSMR_BUS_AGENT= (or
pass =agent_id=) so it never orphans its backlog, and let subagents pass
=ephemeral: true= so they read fresh without consuming the main agent's messages.

* How it works

The bus is durable and broker-mediated, so a missed real-time notification never
loses a message — it degrades to catch-up on the next receive.

- *Broker election.* The first dsmr-mcp process to acquire an exclusive =flock=
  on the bus lock file becomes the broker; every other process is a client.
  Because =flock= is released by the OS when a process dies, a broker crash simply
  lets the next waiter take over — no heartbeat, no manual failover. =flock= is
  per-machine, which is what scopes the bus to a single host.
- *Write-ahead log (WAL) as authority.* The broker is the sole writer; it appends
  every message to a length-and-CRC-framed log under a monotonic sequence number.
  A successor broker replays the log on takeover and truncates any torn final
  record left by a crash, so the sequence is always contiguous.
- *Cursors give exactly-once delivery.* Each participant has a durable cursor file
  recording the last sequence it acknowledged. =bus-receive= delivers every record
  past the cursor and then advances it; =bus-status= reads the count without
  advancing. Cursors are files, so they survive restarts — that is what "resumes
  where it left off" means.
- *Active wakeup.* Real-time delivery rides a ZeroMQ notification, but the wait is
  *level-triggered*: on entry it first checks the log against the cursor, so a
  message that landed between "went to sleep" and "started watching" is seen
  immediately rather than dropped. The notification carries only a sequence
  number; the log and cursor remain the source of truth.
- *Transport.* ZeroMQ over =ipc://= filesystem sockets is the live message path —
  a PUSH/PULL pair fans submissions in to the broker, a PUB/SUB pair fans
  notifications out to subscribers. A dropped or slow subscriber still catches up
  from its cursor, so a lost notification is never a lost message.
- *Orderly archive.* On a *clean* shutdown of the last participant on the host,
  the active log is recovered and rotated to a timestamped archive, leaving a
  fresh empty log for the next run. A crash skips this path by construction, so a
  crash never discards unread history.

* On-disk state

All bus state lives under one directory, rooted at =XDG_STATE_HOME=:

#+begin_example
$XDG_STATE_HOME/dsmr-mcp/bus/        (or ~/.local/state/dsmr-mcp/bus/ if unset)
├── bus.wal                          # the active write-ahead log
├── broker.lock                      # broker-election flock
├── members                          # shared membership lock (held for process life)
├── broker.log                       # broker stdout/stderr
├── cursors/                         # one durable cursor file per participant
│   └── <percent-encoded-agent-id>
├── *.ipc                            # ZeroMQ ipc sockets (submit + pub)
└── bus.wal.archive-<ms>             # rotated logs from clean last-member shutdowns
#+end_example

The directory is shared by every dsmr-mcp process on the host — that is precisely
how cross-project agents find one another. To reset a single participant's
backlog, delete its file under =cursors/=; the encoding is the percent-escaped
identity (e.g. =/home/you/proj/main= becomes =%2Fhome%2Fyou%2Fproj%2Fmain=).

* Configuration

The bus reads two environment variables:

- =DSMR_BUS_AGENT= — the project's stable bus identity (rule 3 above). The shipped
  per-project =.envrc= exports it, defaulting to the project directory name. Set
  it explicitly to pin a different name. Empty is treated as unset.
- =XDG_STATE_HOME= — roots the bus state directory; falls back to
  =~/.local/state= when unset.

No other setup is required. The broker is elected lazily on first bus use, and the
=.envrc= the server offers to write (see
[[file:configuration.org::*direnv per-project setup][direnv per-project setup]])
already carries the =DSMR_BUS_AGENT= stanza.

* Operating it

- *Is the bus up, and is anything waiting?* Call =bus-status=. =broker_running=
  reflects whether a broker holds the election lock; =pending= is your backlog.
- *Drain the backlog.* =bus-receive= with the default (non-blocking) timeout
  returns everything past your cursor and advances it.
- *Broker seems stuck.* Kill the broker process; the next participant contending
  for the election lock takes over and replays the log. No state is lost — the WAL
  is the authority and cursors are durable.
- *Reset a participant.* Delete its cursor file under
  =$XDG_STATE_HOME/dsmr-mcp/bus/cursors/= to make it re-receive from the start of
  the current log.
- *Single host only.* =flock= and =ipc://= sockets are machine-local; agents on
  different machines each get their own independent bus. There is no cross-host
  transport.

* Auto-watch (waking a dormant agent)

An agent process only runs when its harness invokes it; between turns it is
dormant. The bus delivers reliably, but nothing connects /a message arrived/ to
/wake the agent/, so a reply can sit unread until an operator nudges the other
side. The =dsmr-bus-watch= binary is that missing connector: it watches the WAL
and turns a new message into one of the two events a harness can wake a dormant
agent on. Build it with =make bus-watch= and install it on =PATH= via the
installer (=~/.local/bin/dsmr-bus-watch=).

** Two modes

- *Exit-on-event* (default) — polls until a new message arrives, prints one
  =bus:<SEQ>= line, and *exits 0*. Arm it in a background shell whose exit
  re-invokes the agent: the agent wakes, drains the bus, acts, and re-arms.
- *Streaming* (=--stream=) — prints =bus:<SEQ>= once per new message and keeps
  running. Use it under a persistent monitor that delivers each line as it is
  printed (the leader end of a two-agent loop).

** The re-arm rule (load-bearing)

The watcher seeds a /baseline/ sequence number when it arms and fires only on a
seq strictly greater than that baseline. With no author field in the WAL, the
watcher cannot tell your own messages from anyone else's — so the /loop/, not the
binary, is what keeps you from waking on your own traffic. Two rules do it:

#+begin_quote
1. *Arm strictly last — after you publish, never before.* Arming before you
   publish leaves your own message above the baseline, and the watch fires on it.
2. *Re-arm with =--after= OMITTED.* With no =--after=, the baseline is the WAL's
   current max read /at arm time/ — which, because you armed last, already
   includes your just-published message and can never wake you. Do NOT re-arm
   with the seq you were last /signalled/: that value sits below your own newer
   message and re-creates the self-wake.
#+end_quote

The worker loop is therefore:

#+begin_example
bus-receive (drain) → act → bus-publish → bus-receive (catch-up) → arm
#+end_example

The catch-up =bus-receive= immediately before arming closes the only remaining
gap: a message from another agent that landed during your turn, below the
arm-time max. If it returns anything, handle it and loop; if it is empty, arm
(=--after= omitted). Your cursor has then consumed everything through that point
and your own message is in the baseline, so the watch fires only on genuinely new
foreign traffic — never on you.

** CLI surface

#+begin_example
dsmr-bus-watch [--wal PATH] [--after SEQ] [--stream] [--poll-ms N] [--recycle-seconds N] [-h|--help]
#+end_example

- =--wal PATH= — WAL to watch. Default =$XDG_STATE_HOME/dsmr-mcp/bus/bus.wal=
  (falls back to =~/.local/state/dsmr-mcp/bus/bus.wal=).
- =--after SEQ= — baseline; fire on the first seq greater than =SEQ=. Default is
  the WAL's current max seq, read at arm time (=0= fires on any record).
- =--stream= — stream one line per new seq and keep running (else exit-on-event).
- =--poll-ms N= — poll interval in milliseconds (default =1000=).
- =--recycle-seconds N= — idle self-recycle window in seconds (default =600=).
- =-h=, =--help= — print help and exit 0.

*stdout is the signal channel* — only =bus:<SEQ>= (a new message) and =recycle:=
(an idle self-recycle) ever go to stdout; usage, diagnostics, and errors go to
stderr. A usage error exits =64=; a fired or recycled watch exits =0=.

** Idle self-recycle

With no new message, the watch exits cleanly after =--recycle-seconds= with a
=recycle:= line instead of blocking forever. That way a watch silently killed by
a harness restart heals itself: the next arm starts a fresh watch. Treat
=recycle:= as "still alive, nothing new — re-arm".

** Two-agent shape (no operator nudge)

Run the leader with a persistent streaming monitor on =dsmr-bus-watch --stream=;
run the worker with an exit-on-event =dsmr-bus-watch= in a background shell that
re-invokes it on exit. Each side receives, acts, publishes, and re-arms — the
loop self-drives with no operator in the middle.

** Auto-arm on bringup

The two-agent shape above still has one manual seam: *something* has to arm the
first watch. Until it is armed, a fresh agent is deaf on the bus — it will not
wake until its operator nudges it into arming. For the Claude Code harness, the
installer closes that seam automatically: it writes a =SessionStart= hook that
arms the watch the moment a session starts, so the agent is autonomous on the bus
from turn one with no manual step.

*Why a harness hook and not a server-side auto-arm.* The watcher is a /connector,
not an injector/: an exit-on-event watch only wakes the session that *launched*
the background process. The MCP server runs in a different process and cannot
reach into the agent's session to wake it, so the arm has to happen harness-side.
A =SessionStart= hook is exactly that — harness-side code that runs as the session
comes up. This is a hard constraint of how wakeup works, not a stylistic choice.

The hook is written by the installer into the *project's* =.claude/settings.json=
(not the global =~/.claude/settings.json=), so the watch arms only in projects
where dsmr-mcp is installed. The write is *consent-gated* (the installer asks
before touching settings) and *idempotent* (re-running the installer recognises an
existing entry and adds nothing) — the same discipline the per-project =.envrc=
setup already follows. Pass =--no-hook= to the installer to skip the hook entirely.

*** The fd-detachment requirement

A =SessionStart= hook runs synchronously while the session starts. If the watch it
launches inherits the session's standard input/output/error, the session hangs at
startup waiting for those streams to close. The bootstrap arm therefore launches
the watcher with *every file descriptor redirected away from the session*:

#+begin_example
nohup dsmr-bus-watch --poll-ms "$POLL_MS" --recycle-seconds "$RECYCLE_S" </dev/null >/dev/null 2>&1 &
#+end_example

=nohup= detaches from the session's hangup, =</dev/null= closes inherited stdin,
=>/dev/null 2>&1= discards the watcher's own output, and =&= backgrounds it. Omit
any one of these and the session can stall on bringup. The installer ships this as
a small launch script (=~/.local/lib/dsmr-mcp/bus-arm.sh=) that the hook calls, so
the safe form lives in one place.

*** Adaptive cadence

The launch script tunes the watch to the moment by tracking *consecutive idle
recycles* in a small state file and adjusting two independent knobs:

- =--poll-ms= — *per-message reaction latency*: how soon a delivered message wakes
  the agent. Lower is snappier.
- =--recycle-seconds= — the *idle self-heal heartbeat*: how long a quiet watch runs
  before it recycles itself to recover from a silently-killed watch (see
  /Idle self-recycle/ above). This is recovery latency only — it does *not* affect
  how fast a real message wakes the agent.

Keeping the two separate matters: responsiveness comes from =--poll-ms=, never from
=--recycle-seconds=. The script tightens the cadence while an interaction is hot
and relaxes it as the agent sits idle — fast and short when traffic is recent, slow
and long when nothing has arrived for a while. The shipped bands run from HOT
(=--poll-ms 500=, =--recycle-seconds 60=) when a fire just happened, down to IDLE
(=--poll-ms 1000=, =--recycle-seconds 600=) after several idle recycles. These
values live in the launch script and are tunable in place — no rebuild needed to
adjust them.

*** What the hook does, and what it leaves to the loop

The hook only fires the *first* arm — the bootstrap. Every subsequent re-arm
follows the existing re-arm rule documented above (arm last, =--after= omitted,
catch-up receive), driven from within the agent's turns. The hook is purely how the
loop gets started before turn one; it does not change the loop's mechanics.

Identity and the WAL location come from the environment that is already in place —
no new configuration. The arm inherits the project's =DSMR_BUS_AGENT= (so the
bootstrap watch is keyed to the same durable identity as everything else; see
[[file:configuration.org::*direnv per-project setup][direnv per-project setup]])
and uses the default WAL under =$XDG_STATE_HOME/dsmr-mcp/bus/=.
